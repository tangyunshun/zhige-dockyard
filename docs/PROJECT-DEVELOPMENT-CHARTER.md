# 知阁·舟坊项目开发总纲

> 版本：1.0  
> 用途：作为产品、架构、开发、进度汇报和验收的共同基准。每个新任务先读本纲及对应专题规范，再核对当前代码与数据；本纲不替代实现证据，也不把目标写成现状。

## 1. 产品定位与目标

知阁·舟坊是面向软件研发团队的工作空间中枢与研发效能操作系统。它不是单独的 AI 聊天页或静态组件目录，而要连接：

- 账号、个人空间与企业空间，以及成员、岗位、权限、配额和审计；
- 组件发现、装配、输入材料收集、合同约束执行和能力门禁；
- 模型调用、算力资产、任务状态、失败退款、成果物展示与历史追踪；
- 文档/知识沉淀、企业审核、管理员运营与商业化服务。

核心目标是让用户能在真实空间和授权范围内，选择适合业务的研发能力，提供清楚的材料，得到可解释、可追踪、可复核的结果；平台能可靠地记录使用、成本、扣费/退款和运营审计，并在商业规则经批准后形成可持续收入。

## 2. 用户主流程与闭环标准

### 2.1 用户使用闭环

注册/登录 → 创建或加入个人/企业空间 → 查看身份、成员权限、配额与账务状态 → 在组件大厅搜索和选择组件 → 阅读输入要求并提交真实材料 → 服务端验证权限、激活合同、能力、输入和预算 → 执行真实服务 → 持久化任务、用量和成果物 → 在工作台/我的任务查看状态、结果和错误 → 下载、复用或沉淀知识 → 企业内容按规则审核 → 用户查看用量、扣费、退款、充值或订单状态。

每个交付只声称实际完成的链路段。链路中的权限、持久化、恢复、页面状态或账务任一缺失，都必须明确标为未闭环，不能用演示文案掩盖。

### 2.2 管理运营闭环

管理员经授权查看组件合同与能力就绪度、模型部署与价格状态、用户/空间/订单/账务、任务失败和恢复队列、审计日志；具有风险的发布、切换、退款处理、配置和删除必须由服务端权限校验，并保留操作者与变更证据。只读审计接口不得产生副作用或暴露密钥。

### 2.3 生产可用门槛

“部署即可用”必须同时有证据覆盖：生产配置和密钥管理、数据库迁移与回滚策略、认证授权、用户核心页面、API 错误状态、真实持久化、幂等和并发、账务对账/退款恢复、可观测性与告警、备份恢复、隐私安全、容量/成本与运维责任。只通过 `build`、单测或一次模型调用，不足以证明生产就绪。

## 3. 产品与架构原则

1. **先理解、再实现**：先确认业务角色、用户动作、数据来源、权限边界、成功/失败路径和验收标准；需求冲突、写库影响、费用、隐私或外部调用不清楚时，先给出明确假设和风险。
2. **真实数据、真实能力**：页面状态来自 API/数据库；模型能力必须有部署声明和证据；不以 mock、静态成功、占位数据、硬编码组件状态或虚构计数冒充真实结果。依赖不可用时显示阻断/错误，不伪造成功。
3. **合同驱动组件**：组件输入、文件数量/格式、必填字段、输出类型/schema、能力、质量提示和合同版本由组件独立声明；执行服务端读取激活的 PUBLISHED 合同快照。组件 ID 数量、范围、阶段和完成状态不得在页面或统计逻辑中写死，必须支持未来新增编号及非编号 ID。
4. **能力边界诚实**：只声明有部署和真实验证证据的能力。未支持输出类型、OCR/视觉、长上下文、文件分析等必须阻断或明确降级，不能强行按相似类型解析。
5. **安全和权限以后端为准**：前端负责呈现权限结果、加载/空/错误状态；服务端验证身份、空间成员关系、角色、数据归属和敏感操作。高风险写操作需按现有安全规范做确认、审计、幂等与可恢复处理。
6. **小范围、完整纵切**：一次聚焦一个可验收批次；优先完成一个真实端到端用户流程，而不是铺很多半成品页面/合同。保留现有架构和历史数据，不做无关重构。
7. **页面可验证**：凡用户能观察的功能，交付必须说明路由、入口、操作、加载/空态/权限拒绝/失败/成功结果。前端变化应尽量本地启动并给出可访问 URL；不能启动时说明阻碍和替代证据。
8. **错误可诊断**：保留稳定错误码和用户可理解信息；不静默失败，不将异常包装成成功。失败扣费必须原路退款或进入可审计恢复队列。

## 4. 算力、API 与商业闭环

### 4.1 模型与任务

- 浏览器不得指定或覆盖供应商、模型、API key、base URL；由服务端注册表、部署状态、合同能力和平台策略裁决。
- 每次执行要能关联用户、空间、组件、合同版本、执行模式、模型部署、输入/输出 usage、任务状态、成果物和账务流水；敏感原始材料按隐私策略最小化保存。
- 成功条件不仅是 HTTP 2xx：必须验证真实执行模式、合同结构、有效成果物、task/usage 持久化和账务结果。错误路径验证无错误成功任务、无重复扣费、退款幂等和恢复能力。
- 扩展到 60、78、100 或更多组件时，以数据库合同和能力关系驱动，不为编号规模增加硬编码分支。

### 4.2 算力与资金

明确区分底层 Token、平台成本、用户售价、算力点、预扣、实际结算、退款、充值和收入。所有费率单位、舍入、价格来源/版本、生效时间、税费/支付手续费、毛利和异常处理均需明示并可审计；财务计算使用安全整数/BigInt，不以浮点近似账务。

真实 Token 结算、BYOK、售价/加价、支付渠道、会员购买与盈利模型均为独立商业决策和发布门槛。没有负责人批准的定价、单位经济模型、退款/拒付/对账规则及生产验证前：

- 不开启 `settlementEnabled`，不宣称实际 Token 结算已上线；
- 不虚构售价、markup、充值到账、订单成功或平台利润；
- 不把模型成本价 `VERIFIED` 等同于用户售价或盈利；
- 已存在的估算兼容模式必须在 UI 和账单中标明估算属性。

商业化完整闭环需覆盖套餐/服务展示、下单与支付、异步通知验签、入账幂等、额度可用、消费结算、退款/争议、发票/税务要求、管理员对账和收益/成本报表。支付和价格决策未定时，应列出业务决策项及其影响，不自行选供应商或编造商业规则。

## 5. 页面与系统模块验收地图

每个批次判断影响并更新以下链路，不要求无关页面一并重做：

| 模块 | 必须闭环的事实 |
| --- | --- |
| 官网/定价 | 产品承诺与实际能力一致；价格、免费额度、购买按钮和支付状态均来自真实配置/服务。 |
| 认证/个人中心 | 身份、账户安全、资料、设备、会员/订单/账单状态与后端一致。 |
| 空间中枢 | 个人/企业空间列表、创建/加入、配额、邀请审批、待办及空间切换可真实使用。 |
| 空间内部/工作台 | 成员和岗位权限正确；组件装配、材料输入、执行、任务、成果物、文档和空间统计贯通。 |
| 组件大厅 | 搜索、合同就绪提示、收藏/绑定和跳转正确；没有静态假完成状态。 |
| 我的任务/结果 | 展示真实状态、执行模式、合同版本、结果、错误、usage/费用口径；失败任务不可伪装成功。 |
| 管理后台 | 权限、组件合同、模型/价格、用户/空间、订单/账务、退款恢复、审计和只读进度可核查。 |
| 运营与恢复 | 日志、告警、定时任务、备份恢复、结算恢复队列和人工处理流程有人负责且可演练。 |

## 6. 商业化与产品决策清单

以下项目必须进入路线图和状态汇报；不代表已实现：

- 谁付费：个人、企业、按席位、按套餐、按任务、按真实用量或组合模式；
- 如何收款：支付渠道、退款/拒付、对账、发票/税务、支付回调安全；
- 平台如何盈利：模型成本、售价/加价、免费额度、套餐权益、支付/运维/客服成本、目标毛利和亏损上限；
- 用户如何理解费用：执行前估算、执行后实际/估算区分、流水明细、余额不足、失败退款和争议入口；
- 如何维护：模型供应商可用性、费率漂移、容量限制、告警、恢复值班与客户支持。

对尚无负责人决策的条目，按“待决策”报告并说明阻塞的实现范围；不得用默认数字替用户决定。

## 7. 开发节奏与发布门

一个批次按以下顺序推进，并尽可能一次提交完整结果，避免小修小报：

1. **基线确认**：读取本纲、架构冻结/专题规范、真实目录/API/页面/数据模型；核查工作区现有改动，不覆盖他人工作。
2. **范围冻结**：列出目标用户流程、文件/页面/API/表、数据写入、外部成本、明确不做项和完成定义。以用户可见闭环为单位，而非单纯测试数。
3. **实现一个纵切**：合同/服务端权限与验证/API/持久化/账务/页面状态一起考虑；按实际需求选测试和浏览器验收。
4. **证据验收**：针对成功、权限拒绝、输入错误、服务失败、退款/恢复、空态等风险验证；读库脚本必须标注只读，写库/真实模型/外部付费调用必须事先说明影响并纳入批次批准。
5. **上线准备**：迁移状态、配置/密钥来源、回滚、日志告警、手工处置、部署和用户验收说明齐备后，才能称“生产就绪”。
6. **阶段冻结**：交付报告写清通过、失败、未覆盖和下一关口；冻结已签收快照，不因新批次悄悄改写历史结论。

推荐批次规模通常为 2–4 个业务相近组件；安全/账务/跨模块工作按风险缩小。批次不是硬性数量承诺，业务异质时拆开比强行同批更可靠。自动化测试证明机器可判定行为，不代替业务负责人验收。

### 7.1 开发指令发布规范

本总纲不仅约束代码实现，也约束本助手向谷同学、腾同学或其他开发代理发布的每一条任务指令。不得用“继续开发”“把功能做完整”等空泛表述替代任务定义。每条开发指令必须明确：

- 对应的目标用户、业务问题和端到端流程；
- 本批范围、明确不做项、前置事实与需要核实的假设；
- 用户可见交付及涉及的页面/API/数据/权限/账务边界；
- 验收标准、所需测试/只读证据、真实模型或数据库写入是否获批；
- 出现合同冲突、能力无证据、数据风险、费用风险或验收失败时的停止条件和报告格式。

未经明确授权，任务指令不得暗含生产写库、发布/切换合同、真实外部模型调用、产生费用、修改价格/结算/BYOK 或读取/打印环境密钥。多个角色协作时，必须指定负责人、交接物和先后依赖，避免重复探索与相互覆盖。

## 8. 状态与进度汇报口径

任何进度报告至少区分以下状态，禁止合并成一个“完成百分比”：

1. **存在**：目录/页面/API/数据库实体实际存在；
2. **合同就绪**：激活合同版本正确且 PUBLISHED；
3. **可执行**：权限、输入、部署和能力门禁允许执行；
4. **自动化验证**：明确列出测试类型与最近一次通过时间/结果；
5. **真实执行证据**：区分成功与失败、逐组件与共享/临时测试、历史记录与本轮重跑；
6. **当前库内证据**：说明时间窗口、查询条件、归因字段、成功/失败数；不因测试结束清理数据就否认历史测试，也不拿全局数冒充单组件数；
7. **人工业务验收**：记录验收人、时间、样本/版本、通过项、不通过项和签字；
8. **生产就绪/商业闭环**：部署、运营、财务和安全门槛全部有证据后才可使用该状态。

只有明确验收人签署、未完成项关闭且生产门槛满足时，才可称“业务验收完成”或“生产就绪”。不要使用 `COMPLETE` 遮盖待人工确认、未持久化或商业未决事项。

每批只输出一份精简但完整的状态表：目标用户流程、页面可见变化、端到端链路、数据/API、验证证据、成本/风险、未完成项、是否可发布、下一批。测试数量作为证据附属，不作为用户进度主指标。重跑未变化的昂贵/真实模型套件需说明增量价值。

## 9. 决策优先级与冲突处理

1. 用户本轮明确目标、安全边界和审批；
2. 本项目总纲；
3. 对应专题规范（合同/能力/权限/账务/空间等）和已签收决策记录；
4. 当前代码、数据库与部署的可验证事实；
5. 通用模板、旧报告和外部平台惯例。

冲突不得静默择一：简述冲突、影响和建议，涉及付费、生产写库、隐私、合同覆盖、权限、价格或兼容性时等待明确授权。外部大厂做法只作参考，不直接复制与本项目角色/数据/成本不符的设计。

## 10. 当前已知基线与未决项

以下基线取自截至 **2026-09-23** 的批次 2A/2B 报告，属于历史验收记录，不是实时数据库查询；新任务需要新证据时应只读刷新，不可直接沿用为当前事实：

- 组件目录 60 个；批次快照报告 10 个组件有 PUBLISHED 激活合同并满足能力门禁，50 个无合同。C06/C08/C10/C11 的合同与能力“可执行”不等于人工业务验收。
- 2B 冻结快照报告：近 7 天按 `componenttask.type` 归因，C07 有 29 条 REAL_MODEL SUCCESS；C06/C08/C10/C11 各 0 条当前库内成功记录。上一轮有逐组件 REAL_MODEL 测试记录，但不等于本轮重跑或保留的当前库记录。
- 2B 人工签收表列明 C06 财务数值、C08 场景业务完整性、C10 合成/脱敏样例、C11 隔离工程编译运行均待负责人签收；不得自行代填。
- 2B 输出校验报告说明目前明确支持 DOCUMENT 非空校验、TABLE/JSON schema 校验；SCORE/TIMELINE/FILE/DOCUMENT_PACKAGE 会 fail closed，路由当前映射到通用 `RESULT_BUILD_FAILED` 并退款，专用 API 错误码仍是待办，但不因此可发布这些输出合同。
- 报告口径为 `settlementEnabled=false`、`ESTIMATED_COMPATIBILITY`、BYOK 未实现、用户售价/markup 未配置；价格成本记录为 VERIFIED v1 的输入 5/输出 30 CNY 每百万 Token。启用真实结算或确定售价需要单独决策和验收。
- C09 在此前决策中暂停；如无新授权不得进入迁移批次。C12–C15 可作为下一批候选，须先以当前组件目录、数据库激活状态和业务定义复核，不能只靠旧能力矩阵或编号推断。
- 仓库历史文档包含若干可能过期的盘点/架构描述。发现与当前实现不一致时，以实测为准并登记文档漂移；不要把旧文档里的风险陈述直接当成当前漏洞，也不要忽略它们而不核实。

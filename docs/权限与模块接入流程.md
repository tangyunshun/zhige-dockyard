# 权限与模块接入流程（新增模块 / 新增权限 必读）

> 适用对象：后台管理员、后续接手的开发者。
> 目标：**新增模块与权限时"配置即生效"，且绝不会因权限配置把已有功能拦死。**

---

## 一、两层权限体系

| 层 | 载体 | 作用 | 改动方式 |
|---|---|---|---|
| **细粒度权限点** | 权限目录（`systemconfig.PLATFORM_PERMISSION_CATALOG_V1`） | 决定"谁能用哪个功能"，在「权限配置」页勾选 | 注册模块时**自动派生入库** |
| **接口权限规则层** | 接口权限规则（`systemconfig.PLATFORM_API_PERMISSION_RULES_V1`） | 决定"哪个接口路径需要哪个权限点"，由统一拦截层（`src/middleware.ts`）执行 | 「接口权限规则」页配置，**无需改代码** |

统一的代码级守卫（可选）：
- `requirePlatformPermission(request, "键A", "键B")` —— **多键为 OR**（任一满足即放行），用于"细粒度键 ∨ 兼容旧键"平滑过渡；
- `requireSystemSettingsAdmin(request, ...delegated)` —— 超管 + `system:settings` 双校验，可显式声明委派键；
- `requirePermissionGrantAuthority(request, ...actionPermissions)` —— **权限授予类**操作的唯一入口，策略见下。

---

## 二、新增模块标准流程（4 步）

1. **注册模块**：后台「权限配置」→ 注册新功能模块
   - 自动：派生权限点并写入权限目录、按策略为管理员同步默认权限、写入审计日志
   - 自动：生成「接口权限规则」**草稿**（`enabled = false`）
2. **启用规则**：侧边栏「**接口权限规则**」
   - 逐条核对 **路径前缀 / 请求方法 / 所需权限点**
   - ⚠️ 自动草稿的路径前缀是按模块 route 末段推测的（`/admin/xxx` → `/api/admin/xxx`），**如与真实接口不一致必须手工改正**
   - 确认无误后**启用**（不启用 = 不拦截，功能照常可用）
3. **授权**：后台「权限配置」→ 给对应管理员**勾选**新权限点
4. **提交前自检**：`npm run check:permissions`
   - 已接入 **Git 提交前钩子**（`npm run hooks:install`，`npm install` 时自动安装）
   - 已接入 **CI**（`.github/workflows/permission-wiring.yml`）

## 三、自动 vs 人工（明确边界）

| 环节 | 是否自动 |
|---|---|
| 权限点派生 + 入目录 | ✅ 全自动 |
| 按策略为管理员赋权 | ✅ 全自动 |
| 接口权限规则草稿生成 | ✅ 全自动 |
| **规则的启用** | ⚠️ **需人工 1 次**（防止路径猜错导致误拦） |
| **管理员权限勾选** | ⚠️ 按需人工 |

> 设计取舍：**草稿默认不启用** —— 新模块上线**绝不会**因为权限配置被 403，代价是需要人工确认一次。

---

## 四、生效时延（排查"改了没生效"必看）

| 改动 | 生效时延 |
|---|---|
| 接口权限规则（启用/停用/改键） | **约 3 秒**（拦截层 3s 缓存 + 服务端强制读最新） |
| 管理员权限包（勾选/取消） | **最多 5 分钟**（`ADMIN_PERMISSIONS_CACHE_MS = 5min`） |
| 权限目录改动 | 立即（页面实时读取） |

## 五、必须知道的边界

1. **规则层只覆盖 `/api/admin/**`**；前台接口需代码级守卫。
2. **只拦截「已启用」的规则**；草稿不参与拦截。
3. **路径段边界匹配**：前缀 `/api/admin/users/batch` **不会**误命中 `/api/admin/users/batch-logout`。
4. **故障安全（fail-closed，已彻底移除 fail-open）**：规则服务或权限包服务异常时，拦截层对 `/api/admin/**` 一律返回
   **503**（`PERMISSION_SERVICE_UNAVAILABLE`，并带观测响应头 `x-permission-gate: rules-unavailable|context-unavailable`
   与 `Retry-After: 3`），**绝不放行**。
   - 为什么：仅靠规则层保护的后台接口，如果"服务异常 = 放行"，等于权限服务一挂就人人可过。
   - 严格区分两种状态：**读取成功但确实没有启用规则 → 正常放行**；**读取失败/响应异常 → 503 阻断**。
   - 超级管理员不受牵连：其放行不依赖权限包读取（`/api/system/permission-context` 对超管不读权限包）。
   - 平台侧接口 `/api/system/api-permission-rules`、`/api/system/permission-context` 只负责返回状态，
     自身不参与规则层拦截（也不在 `/api/admin/**` 范围内），因此不会递归。
   - 规则写入侧同样收紧：权限目录读取失败时**拒绝保存**规则并返回 503，绝不写入"无法确认权限来源"的规则。
5. **超级管理员无条件放行**，不受任何规则/权限包约束。
6. `posts/standard` 的 GET 为**刻意设计**：仅需登录态（企业空间 OWNER/ADMIN 需读取标准岗位目录做一键装配），**不要**给它加 `/api/admin/posts` 前缀规则。

## 六、权限授予的安全策略（不可穿透）

`src/lib/security.ts`：

```ts
export const PERMISSION_GRANT_POLICY: PermissionGrantPolicy = {
  allowedRoles: ["SUPER_ADMIN"],    // 业务规则：仅超管
  allowPermissionDelegation: false, // 关键开关：permission:manage 等权限点不得穿透
};
```

- **只有超级管理员可以向管理员授予/回收权限**，其他角色一律不行（防止非超管自我提权）。
- 判断逻辑集中在此策略 + `requirePermissionGrantAuthority()`，**不在各路由散落硬编码**。
- 实测：管理员即使持有 `permission:manage` + `admin:permission_grant`，`GET/POST /api/admin/permissions` 仍返回
  `403 {"error":"FORBIDDEN_PERMISSION_GRANT","message":"仅超级管理员可向管理员授予或回收权限","policy":{...}}`。
- 未来若要开放"受控委派"，**只改 `allowPermissionDelegation` 一处**。

## 六点五、接口权限设置是「高危安全配置」（仅超级管理员）

`/admin/permissions/api-rules` 与 `/api/admin/api-permission-rules` 属于**高危安全配置**，规则为：

| 项 | 规定 |
|---|---|
| 查看 / 新增 / 编辑 / 删除 / 启停 | **仅超级管理员**（代码侧由 `requireSystemSettingsAdmin` 强制校验） |
| 普通管理员（含持有 `permission:manage` / `admin:permission_grant` 者） | **不得修改接口规则**；这两个键不得作为修改接口规则的放行条件 |
| 未授权返回 | `403 {"error":"FORBIDDEN_HIGH_RISK_SECURITY_CONFIG","message":"接口权限规则属于高危安全配置，仅超级管理员可查看或修改。"}` |
| 审计 | 所有写操作写入 `writeAuditLog` |
| 前端菜单 | 仅对超管展示；**前端隐藏不构成安全边界**，接口必须强制校验 |

> 为什么这么严：接口规则决定"哪个后台接口需要哪个权限"。一旦非超管可改写，就能把已启用的拦截整体关掉，等于绕过全站后台防护。

**路由守卫说明**：`/admin/permissions` 与 `/admin/permissions/api-rules` 均为超管专属，`AdminLayout` 中已把两者**显式列出**并改为「路径段边界」匹配（`pathname === p || pathname.startsWith(p + "/")`），避免前者前缀"顺带"覆盖后者而产生的歧义。

## 六点六、新增后台 API 的硬性要求

新增任何 `/api/admin/**` 接口，必须满足**二选一**（推荐以代码级为主）：

1. **代码级守卫（推荐）**：`requirePlatformPermission(request, "现有权限点", ...)`（多点= OR）
   - 高危配置域用 `requireSystemSettingsAdmin(request, ...delegated)`；
   - 权限授予类操作用 `requirePermissionGrantAuthority(request, ...)`。
2. **已启用接口规则覆盖**：在「接口权限设置」页配置并**启用**规则（中间件强制校验）。

> ⚠️ **草稿规则不产生任何控制**：新模块注册后自动生成的规则是 `enabled=false` 草稿，
> 在管理员手动启用之前，该接口**不受规则层控制**（仅受自身代码校验约束）。
> 因此"注册了模块"≠"接口已被保护"，必须按上面两条之一补齐。

自检脚本会输出覆盖扫描报告（见下节），确保不再出现"既无代码级权限、也无已启用规则"的接口。

## 七、自检工具

```bash
npm run check:permissions      # 权限接线自检（钩子/CI 调用）
npm run catalog:snapshot       # 导出权限目录 + 接口权限规则快照（CI 无数据库时使用）
npm run hooks:install          # 手动安装提交前钩子
npm run wire:admin-rules       # 为存量接口批量下发规则 + 补授权（幂等，先授权后启用）
```

自检结论的含义：

| 标记 | 含义 | 是否阻断 |
|---|---|---|
| ❌ | 代码引用了「权限目录中不存在」的权限点（管理员无法勾选 → 非超管会 403） | **阻断**提交/CI |
| ⚠️ | 目录中已注册但**代码与规则层都没用到**的权限点 | 仅提示 |

此外脚本会输出**后台接口权限覆盖扫描**（报告，不阻断）：

| 分类 | 含义 |
|---|---|
| ✅ 代码级细粒度权限 | 文件内出现 `requirePlatformPermission` / `requirePermissionGrantAuthority` / `requireSystemSettingsAdmin` |
| 🟡 仅规则层覆盖 | 无代码级守卫，但路径被**已启用**接口规则覆盖（中间件强制校验） |
| 🚨 高风险 | **既无代码级守卫、也无已启用规则** → 必须补 |

验收口径：🚨 应为 **0**。

## 三、根因分析

1. **时间证据**：`_prisma_migrations` 中全部 42 条迁移的 `finished_at` 均集中在 `2026-09-15 12:59:07`——这是一次「从零重建」的迁移回放，而非增量升级；随后 `13:01:40` 又生成迁移 `20260915130140_npx_prisma_migrate_dev`。
2. **binlog 铁证**：`DESKTOP-SMSDPSA-bin.000377` 中存在
   ```sql
   DROP DATABASE `zhige_dockyard`
   CREATE DATABASE `zhige_dockyard`
   ```
3. **机理**：历史上多次使用 `prisma db push` 直接改结构，导致数据库实际结构与迁移历史不一致（drift）。`prisma migrate dev` 检测到漂移后会**重置数据库**（清空全部数据）再回放迁移，并执行 `package.json` 中的 `prisma.seed`。

> 结论：**这不是黑客攻击或硬件故障，而是 `prisma migrate dev` 在存在 drift 时的既定行为。**

## 七、经验教训

- `prisma migrate dev` 仅适用于**开发期可随意重建的库**；一旦库里有真实数据，必须改用 `migrate deploy`，否则 drift 会触发毁灭性重置。
- **备份是唯一可靠的兜底**：本次能得救，纯粹因为系统开启了「系统保护/卷影副本」。
- **binlog 不等于备份**：没有基础全量备份时，binlog 无法完成全量恢复（且默认仅保留 30 天）。

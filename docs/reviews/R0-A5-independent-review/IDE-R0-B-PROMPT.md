## 2. 已证实的问题

- src/lib/payment/fulfill.ts中的SEAT_ADDON分支。
- src/app/api/payments/mock/confirm/route.ts中的独立SEAT_ADDON分支。

两者先在事务外读订单为PENDING，再在事务中直接增加extraSeats；两个请求都读到PENDING后，即使事务串行，仍会增加两次。本轮隔离执行真实代码，2席位订单两次确认最终增加4。

两者在事务回调内部调用的是根billingModel.update，不是tx对应的账单模型，订单状态可能脱离席位事务。不能仅把更多代码包进$transaction却继续用根客户端。

只在页面禁用按钮、使用进程内锁、或先读状态再判断，都不能保证跨请求/多实例正确。

## 4. 服务端必须实现的业务保证

### A. 只有一个并发请求获得该订单的履约权

在数据库事务的写边界，用已有schema支持的可靠方法（例如带PENDING条件的原子更新及count判断，或适合当前数据库的行锁后重验）裁决同一订单。

- 胜出者才可增加席位并记录该次履约；其他请求不得再次增加。
- 已完成的重复通知应返回与既有调用契约兼容的“已处理”，不能报再次加席位成功。
- FAILED/EXPIRED/REFUNDED等不合规状态不得被覆盖成SUCCESS。
- 如果事务竞争结果需要重读，在正确边界重读并区分已完成、不可处理、暂时冲突；不靠内存去重。
- 不新增公网“强制入账/跳过状态”参数；不信任客户端paid/seats/amount作为付款凭据。

### B. 订单状态、席位和本次履约记录使用同一个事务客户端

- 席位增量和订单成功状态在同一事务提交或回滚。
- 所有相关写入使用tx模型；模型别名辅助函数若保留，应明确接受事务客户端，不闭包捕获根客户端。
- 在“状态更新后席位失败”“席位更新后状态失败”“提交失败”等可模拟场景中，不得出现SUCCESS但未增加席位，或PENDING却已增加席位。
- 故障后保持可诊断、可安全重试；不吞异常并返回已完成，不擅自退款/改历史账。
- 需要的审计/metadata基于既有字段，保留订单号、空间、席位数、付款模式/交易号等事实；避免每次重复请求重写不同付款事实。

### C. REAL与MOCK共享同一份席位入账规则

可以复用/抽出最小SEAT_ADDON履约函数；不能留下两份状态机分别修一半。

- 微信/支付宝仍先验签、校验付款状态，再调用受控服务；不得为测试放宽验签。
- MOCK仍受resolvePaymentMode门禁、登录和订单归属保护；REAL环境不能通过模拟确认席位。
- 原充值与套餐升级分支的既有行为不被全局重构改变；用必要保护回归说明。
- 不因复用服务把模拟付款标成真实收入，也不改环境配置启用MOCK。

### D. 在发权益前校验本订单的可信数据

- SEAT_ADDON类型、明确workspaceId、订单归属/空间关系按现有业务边界核对。
- 持久化seats为正的安全整数，不能接受小数、NaN、负数、溢出，也不通过Math.floor把损坏订单猜成有效。
- 校验与数据库Int范围及既有extraSeats相加的合法性，不能因溢出产生错误权益；不凭空设置商业席位上限。
- REAL席位付款必须有经过受控回调验证的合法实付金额，与订单分金额一致。缺失、非法、不一致不发权益；不对全站其他支付类型做无关变更。
- 保留到期/订单生命周期规则；套餐到期、空间被删除/归档、类型变化、权益截止时间不匹配等异常不能静默授予错误席位。按现有规则拒绝/报告人工处置，不创造新退款或延期政策。
- 付款已发生但无法履约的异常要返回可重试/可诊断错误并保留订单证据，不能把“没发权益”声称为“用户没付钱”。

### E. 页面与结果诚实

- 创建PENDING订单只显示待支付，不能立刻显示席位到账。
- 实际履约一次后显示真实增加量；重复确认只显示该订单已处理，不让用户以为再次购买/到账。
- 失败保留订单号与说明；不自动重复下单，也不以本地存储冒充实际席位。
- 若现有页面已满足，保持页面代码不动，给出源码/行为验证证据即可。

## 5. 必须提供的隔离验证

不得mock掉本次修的席位核心服务。只替换数据库、认证、网关验签输入等IO；明确模拟验签结果不是实际交易。定向测试至少覆盖：

| 场景 | 验收结果 |
| --- | --- |
| 单次有效2席位订单 | 总增量2，状态SUCCESS，结果/metadata正确 |
| 同一订单两次及多次并发确认，强制都先读到PENDING | 最终仍只增2；仅一次实际履约，其他已处理/按规范重试；不能只测串行重放 |
| REAL服务、MOCK接口及二者共享调用路径 | 同一状态机，去重保证一致，无双份独立加席位逻辑 |
| 先成功后重复通知 | 零新增权益、无重复成功记录/伪付款 |
| 事务各写点/提交故障 | 订单与权益同回滚；重试后恰好一次；禁止根客户端写逃出事务 |
| 不同订单同一空间并发 | 每笔合法订单各增加一次，总量正确，不能互相覆盖 |
| 非PENDING、超时、损坏席位数、缺空间、异常金额等 | 无错误席位/账单成功，明确说明 |
| REAL缺金额/金额不符，MOCK被REAL门禁阻断，未登录/他人订单 | 无权益写入；权限和验签门禁不变 |
| 异步回调失败/重复的响应 | 维持各支付渠道既有ACK/重试约定，不能假成功吞掉未履约订单 |
| 充值/PLAN_UPGRADE与R0-A保护 | 必要回归不退化，不擅自改其商业规则 |

内存Prisma要记录事务内/外调用和最终状态，并真实模拟条件更新、并发竞争与回滚；不能所有updateMany都返回count1，不能$transaction仅执行回调却宣称测试了回滚。可以设计封闭stub让任何根客户端写直接失败，以发现事务外更新。

本库部分测试直接写真实MySQL。先审导入链，只运行指定的安全测试文件和本地tsc --noEmit --incremental false；禁全量测试，不临时下载依赖，不连真实库。没有真实MySQL验证就明确并发/锁/提交语义仍待专门验证，不冒充生产幂等验收。

## 6. 商业边界与停止条件

本批解决“同一订单多发席位、状态与权益分离”，不等于证明席位报价盈利。

现有seat-addon把套餐月价折算进不同计费周期，涉及月年单位、剩余天数、舍入、最低收费/0元等商业问题。先列真实公式与风险，不在本批自行乘12、调价格、补历史差价或增加优惠。发现不能确定金额合法的请求/存量订单，安全拒绝并列待业务决策，不为通过测试编价格。未审批的价格/利润模型不发布。

不处理真实回调重放攻击体系、退款争议或全局认证重构，不改付款服务商/密钥或读取环境连接串。若故障恢复必须真实写库、新表/迁移、人工退款或改变收费政策，停止相关操作并说明；已有可安全处理的代码和隔离测试先完成。

# 给 IDE 的 R0-J1 修复提示词：补齐原 F13，禁止扩展到 F14

## 任务定位

先读项目开发总纲、上一批 `docs/reviews/R0-J-preflight/IDE-R0-J-PROMPT.md` 的 S01—S08，以及本目录 REVIEW.md 和三份运行证据：handler-verification.json、path-verification.json、ui-verification.json。

当前 R0-J 未通过独立审核。433 项正式回归和类型检查通过，但独立故障/交错验证确认原验收范围仍有遗漏。本轮只修这些遗漏，不新增商业功能、不更换架构、不进入 F14，不将改写报告或增加测试数量当作修复。

目标仍是：授权用户上传文件不突破空间额度，失败可恢复；彻底删除只释放一次，清空不丢失新上传/失败对象记录；私密资料归属不被绕过；页面和对账反映事实。

保留已通过的配额语义、JSON 不采信伪造 fileSize、普通有限额度的原子竞争、新本地路径、正常附件保存和 EACCES 失败呈现。禁止改价格、套餐额度、算力点、支付、BYOK、生产结算开关以及 F11/F12；handler 只改存储相关分支，不重构执行核心或解析器。

## A. 先冻结本轮实际版本

保存实际要改文件的完整起点副本、SHA256 和真实时间，创建 `docs/reviews/R0-J1-fix-snapshot/manifest.json`。以 J 的真实结束哈希作为起点核对参考，不重跑旧 capture-facts 去覆盖原审核目录。

主要修改范围：storage-quota.ts、file-store.ts、Studio 的现有存储分支、clear-data 的文件/存储段、两处直接相关批量回调和必要测试。为了持久恢复允许最小必要的存储操作字段/记录及离线迁移草案，这已在原 S02/S08 范围内；优先复用现有模式，不建通用调度平台。不得执行迁移或在用户请求中自动 DDL，结构未就绪诚实拒绝。

## B. J-UPLOAD：让预留、对象和记录真正可恢复

1. opId 必须关联持久化的空间、操作者、对象定位、实际字节和状态，实际参与去重/确认/释放。不能只是响应里的随机 UUID，也不能仅增加参数但不使用。重启后仍能定位未完成操作；同操作重试不重复占用。
2. 目标对象定位要在发生外部写入之前可追踪。底层保存已产生字节后报错、超时或响应丢失时，不能因 saved=null 就认定“没有对象”并释放容量。保留待核实占用，确认对象状态后再安全完成或清理。
3. 两条上传必须把实际文件保存、document 创建/提交、确认和失败恢复覆盖完整。现在 document.create 在清理 try 之外，应修复这两个分支。记录/确认失败不能留下无关联文件和不可恢复的余额差异；清理失败需持久状态，不能只在 HTTP 返回一句“已保留恢复信息”。
4. 上传内部状态不得冒充审批 PENDING 或成功资料。错误响应须与已完成/未知事实一致，保留稳定错误码；可重试恢复须有身份/空间边界和幂等，不开放任意用户释放别人的占用。
5. 普通上传目前解析两次且在空间鉴权前解析。先做现有身份、归属、必填和容量准入，再执行一次必要解析；只调整本分支调用顺序，不开发 F14 解析能力/限流。解析失败也进入同一存储恢复协议。
6. 保留 JSON 文本正常创建。真实 0 字节文件的元信息应是已知 0，不能归一为未知大小后造成对账失真。

## C. J-RELEASE：业务状态和额度只提交一次

1. 所有彻底删除入口都使用同一可靠协议。物理对象确认删除/不存在之后，通过文档或操作状态的条件变更与配额更新形成原子提交，决定唯一一次释放；不能 release 后再无条件 delete 记录。
2. 两个相同文档的并发请求、删除与清空竞争、释放成功但删记录失败、提交失败及重试，都不得重复减容量。已确认的物理删除若后续数据库失败，记录/操作保留足够状态，后续只能完成未提交部分。
3. 移除 storageUsed 不足时自动 SET 0 的后备分支。差异应保留、报告并阻断危险释放；不能用 drift=true 为清零开脱，也不能在调用方忽略异常后返回全部成功。
4. 同一物理对象存在重复引用时，不得按文档条数重复释放或删除仍被保留引用使用的文件；未知历史引用关系先报告并阻断危险释放，不借本轮建立新的去重产品功能。
5. 软删除/公开移除继续占用，恢复不重复加；无物理文件的文本不释放历史伪造字节；大小未知对象不当作已准确释放。

## D. J-CLEAR：限定清理集合，失败和新上传都不能丢记录

修复 `POST /api/workspace/clear-data`：

- 不允许扫描一批后执行全 workspace 的无条件 document.deleteMany。
- 只对本次被安全认领、实际核实成功的对象/记录完成删除和一次释放；物理失败或待核实对象保留记录、状态及占用。
- 对扫描后新上传的资料，保证完整保留，或在开始新增占用前由明确协调拒绝；不能上传返回成功后再删除其记录并留下文件。
- clear-data 与另一清理/删除请求交错时也只释放一次。部分失败返回实际成功、失败或待处理结果，不再假报“已成功物理重置”。
- 只改文件与容量闭环及相应结果说明，不借此重写任务、组件初始化、审计清理等其他重置规则。

## E. J-PRIVATE：保留既有私密资料隔离

batch_delete_assets 除空间成员/治理权限外，必须遵守邻近删除分支的 PRIVATE 仅上传人本人规则。空间所有者/管理员不得因此批量删除其他人的私密资料；跨空间文档继续拒绝或跳过。按单项返回实际结果，与既有公开资料治理/删除申请要求一致，不重新定义 RBAC。

## F. J-KEYS：本地历史路径和 S3 同一对象契约

1. 当前 S3 PUT 为 assets/w1/uuid，GET/DELETE 为 w1/uuid。修复对象键契约，SDK 夹具必须观察三种命令定位同一对象；不能靠实际桶测试或仅本地路径测试证明 S3 通过。
2. 兼容本批前已确认的本地双 assets 实际位置，以及原附件单层位置。候选不存在不能直接视为目标不存在。已知位置仍可能存在时，不释放占用、不删恢复依据。
3. 路径解析限制在存储根和对应空间。未知驱动/历史位置或多个候选有歧义时，诚实报告待核实，禁止自动迁移、移动、批量扫描删除真实历史对象。不要新增客户端任意指定对象 key 的能力。
4. 保留新上传本地 save/read/delete 一致和非 ENOENT 失败结果。修复不能再引入第二套附件直接写盘流程。

## G. J-WRITE-BOUND：所有额度语义在实际写边界核验

不能在读取 -1 后无条件 increment。统一处理当前可信 -1、正上限、0、非法/负用量和并发变更，实际写入使用最新事实。正常 -1 到 0/有限额度的收紧，以及用量在读后变为非法值时，不能继续按旧快照放行。保持 BigInt 和数据库级原子竞争，不改套餐配置或发放无限权益。

## H. J-PARTIAL：后端结果接到现有页面

batch_delete_assets 和 batch_remove_assets 返回可直接用于刷新的实际成功 ID、失败 ID/原因、跳过 ID/原因，保留必要旧字段兼容。两处真实前端回调处理 207/业务部分成功：成功项更新或刷新，失败/跳过项保留且可重试，提示数量和原因。不按全部请求 ID 删除，不在 success=false 时只抛普通错误并留着所有成功项。只调整相关回调/状态，不重做页面。

## I. J-RECONCILE：只读报告说清已核实与未知

- 以规范化且包含驱动/空间边界的唯一对象身份去重求和，报告重复引用、冲突大小和未知大小，不按行数当物理对象数。
- 纳入持久预留、确认、清理待处理状态，区分已用与在途事实，不把正常在途简单归为历史漂移。
- 用可注入的只读对象清单/元信息支持发现缺文件、孤儿对象和真实大小差异；没有物理核查时明确显示未核实，不能 notes 为空且暗示已对上物理存储。
- 比较未完成或信息未知时，不返回“已完整对账”的语义；报告可部分计算但明确覆盖范围。
- 对账仍零写、零删除、零自动释放。可交付最小读取函数加夹具和运行说明，不要求新建后台页面、调度平台或实际定时任务。

## J. 必须提供的正向验收，不能用本目录缺陷复现 PASS 冒充通过

| 原缺陷 | 修复后必须证明 |
| --- | --- |
| 两条上传 document.create/提交/确认失败 | 安全清理，或有持久可恢复占用/对象关系；无假成功、无不可追踪文件 |
| 保存已写字节后抛错/超时 | 未核实之前不释放真实可能占用；重启后可核实恢复 |

| 同文件两个删除、删除与清空竞争 | 文件只释放一次，别的文件占用不被扣；受控屏障安排交错 |
| 释放/删记录/事务提交失败后重试 | 不假报成功、不重复扣减；持久状态/余额一致 |

| 清空物理删除失败 | 对象、记录、占用和失败结果对应，不能只留余额丢文档 |

| 批量管理员操作他人 PRIVATE / 跨空间资料 | 拒绝或跳过且零物理删除、零错误释放 |
| S3 SDK + 新本地 + 已知历史位置 | 相同逻辑对象保存可读、删除可核实；歧义不误释放 |

| 重复引用、在途/待清理、缺对象、孤儿、未核查 | 对账唯一对象计量，未知诚实、只读方法零写 |

使用实际 handler/service、实际配额逻辑，仅外部 DB/fs/SDK/解析器 IO 夹具。数据库夹具需真实求值状态条件/事务提交与回滚，记录普通写和 raw 调用；不能 mock 整个业务服务返回成功，不能只做顺序重试证明并发安全。S3 用假 SDK；本地可用内存 fs/隔离临时目录，禁止真实用户资料。

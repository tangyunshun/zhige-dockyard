## 逐项事实与运行证据

### 1. J-UPLOAD：响应里的 UUID 不是可恢复占用记录

storage-quota.ts:108 接收 opId，但未用于持久化或去重。handler.ts:4581、6485 生成的 storageOpId 仅在部分错误响应出现，未关联到持久化操作状态；文件保存函数还会另生成对象 UUID。

普通上传的清理 try 在 handler.ts:4584—4617，document.create 位于 4639，已在其外；附件清理 try 结束后才在 6510 创建文档。两条真实 handler 的 document.create 故障注入均得到 500，留下一个 3 字节对象和 3 字节占用，没有对应文件文档或可恢复操作记录。附件仅剩原父条目。

模拟底层写入已经产生字节、随后抛错：saveAssetFile 未返回路径，saved 仍为 null，handler.ts:4600—4601 直接释放预留。结果响应 500、实际对象仍有一个、占用变成 0。这条分支会使后续上传绕过实际占用。

同一 opId 两次 reserveStorageBytes 各 30，实际占用变 60，没有持久化去重。不能用返回 storageOpId 声称满足原来的重放/重启恢复验收。

此外，普通 multipart 在约 4542 行先解析一次，4593 行又解析一次。实际成功请求解析夹具被调用两次；不存在空间的请求返回 404 前也调用一次。移除重复并将本次材料解析放在授权和容量准入之后即可，不要求改造 F14 解析器。

### 2. J-RELEASE：原子减法不能替代业务幂等

handler.ts:4873 在 document.delete 前释放；5684、5813、5883 同样未与文档/操作状态条件、提交结果绑定。两个真实 remove_asset 请求在同一个文件上交错执行，原占用 100，删除目标 30，另有真实文件 70；结果占用为 **40**，另一文件仍有 70 字节。一个响应 200，另一个 500，也无法撤回已经多减的占用。

单次删除 document.delete 失败时，当前 catch 把记录改成 REMOVED 并返回 200；该记录仍在，而占用已释放，后续重试没有“已释放”持久状态。

storage-quota.ts:193 的后备 UPDATE 还会将不足扣减的 storageUsed 清零。独立夹具 used=10、请求释放 30，得到 0；返回 drift 标志不能使错误清零成为安全。原要求明确不以钳零掩盖差异。

### 3. J-CLEAR：清空删除的记录范围超过已核实对象

clear-data/route.ts:97 读取快照，逐个删除文件后，第 113 行仍执行 `document.deleteMany({where:{workspaceId}})`。

- 物理删除失败：文件保留且占用 30，但文档被删除，接口 200/success=true，恢复线索丢失。
- 真实并发上传在快照扫描后、原文件删除前完成：上传成功且新对象存在，之后 deleteMany 把新文档也删掉；清空响应仍 200，新文件 3 字节成为无文档对象。

该证据调用实际 clear-data 和实际 upload_doc，通过 IO 屏障安排交错；不是把新数据直接伪造成成功响应。不能用“单条扣减原子”代替此业务竞态测试。

### 4. J-PRIVATE：管理员批量接口绕过既有私密隔离

batch_delete_assets 在 handler.ts:5795—5816 核对治理身份后，仅按 id/workspaceId 取文档并删除。没有邻近 remove_asset、batch_remove_assets 中的“PRIVATE 仅上传人本人”限制。

独立夹具：u1 为本空间所有者，目标为 u2 的 PRIVATE 文件，批量接口返回 200，文件、记录和占用都被删除。应按既有政策拒绝/跳过该项，不扩大管理员权限，也不新做 RBAC。

### 5. J-KEYS：S3 与历史本地对象仍分叉

file-store.ts:100 的 S3 PUT 使用 `assets/w1/uuid.txt`，152 行规范化后，157 行 GET 和 136 行 DELETE 使用 `w1/uuid.txt`。独立 AWS SDK 传输夹具确认 GET 缺对象，DELETE 返回成功但原 PUT 对象仍存在。没有真实云请求。

本地新文件路径确已修正，但历史保存到 `uploads/assets/assets/w1/legacy.txt` 的对象，当前读删只访问 `uploads/assets/w1/legacy.txt`。独立内存 fs 中，读取失败，删除返回 ok=true/notExists=true，旧文件仍在。需兼容已确认历史位置或明确阻断待核实，不能把错误候选路径的不存在当作目标对象已不存在。不得自动移动或批量清理真实历史文件。

### 6. J-WRITE-BOUND：不限量分支依赖过期快照

storage-quota.ts:128—135 在读到 -1 后直接 update increment，没有在该写入动作中检查最新限额。夹具在读取后将上限从 -1 收紧至 0，预留 60 仍成功，用量 60/上限 0。原 S02 已明确要求限额/用量并发变化在写边界核验。

应使用统一且含有效用量/限额语义的写边界判定，不能只保证普通正限额竞争安全。

### 7. J-PARTIAL：部分成功没有在页面兑现

WorkspaceInternalLayoutV3.tsx:3478、3665 两处实际批量回调遇到 success=false 即抛错退出；207 本身是 HTTP ok，仍会因业务字段退出。独立执行实际回调，服务端已成功删除一项、失败一项时，两项都留在本地列表，仅显示普通错误。完整 DOM 未验证。

响应也未给出统一的成功 ID 集合，旧回调成功分支是按全部请求 ID 移除。应按实际成功/失败/跳过 ID 更新或刷新真实列表，不只给服务端加 failed 字段。

### 8. J-RECONCILE：报告与实现能力不一致

storage-quota.ts:332—343 遍历每条文档累加，没有按对象唯一身份去重。两条记录引用同一个 30 字节对象，报告求和 60，形成错误差额 -30。

不传 fileExists 的正常夹具 notes=[]，未标明物理存在性/大小/驱动未核验；仅给“是否存在”回调也无法发现数据库没有引用的孤儿对象，且没有持久预留/待清理状态参与核对。当前报告声称“按唯一对象、孤儿/在途状态、未核验明确标注”不成立。无需重建运维平台，只需补原 S06 的最小只读报告契约与夹具。

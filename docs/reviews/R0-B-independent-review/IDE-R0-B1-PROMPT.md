## 2. F1：超时与履约必须竞争同一订单状态，不能覆盖SUCCESS

当前三个位置基于旧PENDING直接按id改EXPIRED：fulfill.ts、mock/confirm和新共享服务。独立验证发现：另一请求已提交SUCCESS和席位，旧超时分支仍改成EXPIRED。

必须满足：

- 席位路径的外层入口不能先运行绕过共享规则的无条件超时写；在识别SEAT_ADDON后适当收敛到同一状态处理边界，保留MOCK登录/归属/模式门禁和REAL可信回调校验。
- 过期转换只允许实际仍为PENDING且符合截止条件的记录；正常履约争取权与超时关闭互斥。竞争失败按最新状态分类，不把SUCCESS/REFUNDED/FAILED等改为EXPIRED。
- 对订单截止时间的最终判断与写边界保持一致，不只在事务前看时钟。既有生命周期规则保留；不自行增加迟到付款的退款/延期政策。
- 不用catch吞掉状态写失败后宣称已经关闭；不论状态更新在哪个入口，都不能破坏已完成权益。
- 事务异常/提交结果不确定时，不无条件断言“数据库一定保持PENDING”或让用户再买一次。返回可诊断的未确认/可查询状态，重试同一订单仍不多发；不新增自动退款或补账。
- 修改共享生命周期helper如确有必要，明确对其他订单类型的影响，作最小保护回归，不借机重写全站订单状态机。

## 3. F2：在实际写入边界核验空间与可信报价，不默许缺字段

当前服务不读取status/plan/planBillingCycle；归档停用空间也发权益，metadata.expiresAt缺失跳过校验；事务前检查后空间类型/套餐基准变化仍能增加席位。

要求：

1. 正确核验空间存在、按现有规则可写、企业类型、订单目标/关系，以及当前套餐身份、计费周期、截止时间与订单记录的可信报价一致。
2. 报价planKey/billingCycle/expiresAt等必要事实缺失、非法、变更，不默认当前配置补齐或猜成有效，明确拒绝并列人工核查；不写历史订单或擅自退款。
3. 使用合适的事务读取/锁或带关键事实条件的workspace更新，在最终写边界确保检查仍成立。仅把findUnique移到tx内、之后按id盲写，不能解决检查后的并发变化。
4. 状态改SUCCESS、席位更新、履约metadata继续使用同一tx；资格失效/条件竞争失败必须一同回滚，不能成功订单无权益，也不能无效空间有权益。
5. extraSeats相加范围/正安全整数在可信边界核对，考虑不同订单同空间并发。不要凭空设商业席位上限，不把普通内存数字运算冒称验证了MySQL Int约束。
6. 无法确定原报价或业务关系时安全拒绝并说明，不在本批决定继任所有者、旧套餐订单自动迁移、价格补差等新政策。

## 4. F3：打通真实微信席位订单的二维码载体

实际网关返回payUrl为本地QR页，gatewayPayload.codeUrl为二维码地址；seat-addon route丢弃后者，查询GET只读metadata.codeUrl，最终为null。

- 沿现有订单与本人查询契约安全保存/读取服务端网关返回的必要codeUrl等支付展示事实，不接收浏览器自传地址，不保存/返回整个敏感网关payload或证书密钥。
- 微信成功下单后的本人订单查询能读到正确codeUrl，收银台能据此生成二维码；支付宝跳转和MOCK原有契约保持。
- 保存载体不得覆盖并发履约metadata、seatsAdded、paidAt或订单状态；只改必要字段/使用合适状态条件，竞争完成时按最新事实处理。
- 网关失败/缺二维码/保存失败时明确说明未能准备收银台，不伪装可付款、不无限转圈、不自动重下单；订单证据保留供重试/人工核查，不自动清账。
- 不接真实微信/支付宝、不新增渠道或改环境。验收使用符合实际网关返回类型的IO夹具，不能只stub一个payUrl而省略载体。

## 5. F4：页面按真实状态及商品类型展示，不泛称成功或算力到账

模拟页当前status!==PENDING就显示已支付，导致过期/失败/退款均绿色成功；真实QR页对席位订单显示算力到账和点数流水。

- 仅明确SUCCESS展示相应完成结果。PENDING、EXPIRED、FAILED、REFUNDED及未知状态分别显示真实含义、合适操作；不能把所有非成功都显示等待支付。
- 按订单type及已有可信字段区分席位、算力充值、套餐开通；席位成功显示席位结果和对应空间/账务入口，不说算力到账或引导点数流水。未知类型用中性文案，不猜权益。
- 订单查询已有type/seats字段，优先使用既有契约；确需补workspaceId等本人订单字段时作最小扩展，不暴露他人数据或支付敏感内容。
- 付款已发生但履约未确认时诚实提示查询/处理，不让用户再付一次；未成功状态不设置本地SUCCESS。
- 支付载体缺失或失败有明确错误/重试边界，不无限加载。
- 可以保持现有布局，不做全站支付UI重构。

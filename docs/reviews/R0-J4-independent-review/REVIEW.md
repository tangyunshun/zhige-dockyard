## 3. 剩余问题与可复现证据

### J3-01 / P1：单项恢复没有共享引用检查，会误删仍在使用的对象

位置：`src/app/api/studio/handler.ts:4848`，特别是4851–4856。文档不存在时，找到pending就直接删除物理文件，再释放占用；清空恢复新增的引用保护没有接到这个入口。

独立记录 `single-recovery-shared-defect`：d1已删，有其30字节待清理认领；d2仍以 `assets/w1/x.bin` 引用同一对象。重试删除d1返回200/pendingCleared=true，d2仍在，文件消失，used=0。

影响：存活资料不可读取、占用错误释放。上一轮要求每次外部删除都执行相同真实对象引用规则，新增恢复路径也受其约束。清空共享保护本身已核实通过，不再重做。

### J3-05 / P1：文档缺失后管理员恢复绕过他人私密资料限制

位置：`src/app/api/studio/handler.ts:4851` 的 `pending.userId === userId || isManager`，以及4879处正常私密限制。

独立记录 `private-recovery-authority-defect`：企业空间所有者u1、成员u2；u2私密资料仍存在时u1删除得到403。随后构造由u2发起、文档已删的待清理状态，u1再次请求相同assetId却得到200，u2认领RELEASED、文件删除、用量释放。此用例验证的是持久恢复状态下的权限，不声称执行了u2的完整删除请求。

影响：同一权限因文档是否存在而变化。恢复记录缺少可以证明“允许管理员代为恢复此对象”的权限事实，不能把isManager作为统一通行证。原提示词明确要求不因文档缺失放宽私密权限；本项是新增恢复入口的回归，不是重新设计权限。

### J3-03 / P1：清空漏接blocked与原始大小；重开分支仍先破坏、后报冲突

位置：`src/app/api/workspace/clear-data/route.ts:157`、166–189；`src/lib/storage-quota.ts:490`–505。

三条独立记录：

1. `clear-unknown-size-defect`：fileSize=null、文件30、used=30。clear-data传入 `d.fileSize ?? 0`；文件和文档被删，认领bytes=0/RELEASED，used仍30；返回200并提示纯净出厂状态。单项删除的null保护没有覆盖清空。
2. `clear-blocked-ignored-defect`：已有认领bytes=30、文档fileSize=50。service返回blocked，但clear-data没有处理该状态，仍删文件和最后文档；之后finalize才报漂移。用量保留并不能补救被禁止的资料删除。
3. `cancelled-size-conflict-defect`：CANCELLED认领bytes=30、文档fileSize=50。claimObjectCleanup先重开并返回claimed，未执行后面大小核对。单项删除据此删掉文件/文档，最后才返回500/漂移，用量30仍在。

影响：历史未知/矛盾数据不能按原要求“先保留再核实”，在故障资料上产生不可逆删除。保持真实0字节正常可删，不得一律禁止零大小。

### J3-02 / P1：清空仍关闭共用认领；终态重放仍误判漂移

位置：`src/app/api/workspace/clear-data/route.ts:184`；`src/lib/storage-quota.ts:545`–574。

- `clear-remove-concurrency-defect`：A清空创建认领后停在文件删除前；B单项删除读同一资料，删文件/文档后暂停；A继续，删行count=0，因自己曾返回claimed便把共用认领CANCELLED。A返回200“纯净出厂状态”；B终结CAS失败返回500。最终文档/文件无、used=30、CANCELLED。创建过认领不等于独占执行权。
- `released-replay-defect`：释放30后used=0、操作RELEASED；再次终结同操作，先尝试扣量、发现不足便返回drift=true/alreadyReleased=false。原提示词已要求终态先识别，避免把已完成重放当成新漂移。

同类两个remove_asset交错已在本轮通过；剩下混合入口不能遗漏。数据库事务无法补救在事务外被另一请求取消的共用状态。

### J3-04 / P2：查询失败仍伪造1条待处理，数量未知标志未进入结构化结果

位置：`src/app/api/workspace/clear-data/route.ts:142`、232–233、251。

`unknown-count-defect`：夹具中实际没有任何认领，让pending列表查询失败。响应同时声称“1条历史待清理认领仍未完成”和“数量未知”，storage.pendingStill=1；recoveryCheckFailed只作为局部变量进入文案，没有进入storage结果。

已修好“不再报完整成功”，但“未知时不编造数量”未完成。查询失败无法证明有0/1/N条；失败检查次数应与实际认领条数分开表达。本项是同一报告口径的小范围收尾，不需新增运营页面。

### J3-07 / P2：新增恢复查询没有接入就绪错误与HTTP映射

位置：`src/lib/storage-quota.ts:598`–604，`src/app/api/studio/handler.ts:4850`及7699–7714外层catch。

`missing-schema-recovery-defect-P2021` / `...-P2022`：文档已无，恢复查询findFirst分别抛缺表/缺列。实际remove_asset都返回普通500、无稳定code；文件、用量保留。当前证据未发生对象副作用，不夸称已造成损失。

findStorageOp已处理的错误没有覆盖findStorageOpByDocument；只在service改抛StorageQuotaError也不够，实际handler还要返回其状态与code，避免又掉入普通500。

## 4. 为什么493条通过仍不足以验收

新增正式用例主要覆盖单项正常分支。标作并发的测试直接让deleteMany返回0，再用清空收尾，未实际交错清空与删除；P2002命名用例实际仍是顺序重复调用（本轮另行补了真实create唯一冲突的独立核验，类型校验已通过）；大小保护未测clear-data和CANCELLED；恢复权限只测跨空间，没有测同空间其他用户私密认领；缺列只测service，没有覆盖新增实际恢复API。

这些缺口都在上轮明确要求的入口/分支中。不是把正常路径修复否定，也没有引入F14或新的商业需求。

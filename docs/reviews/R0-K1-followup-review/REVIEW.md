## 2. 未完成项：只沿用原编号

### A / P1，原 KR1、KR4：未知停止状态未完整隔离，OCR 仍可挂起

当前 handler 三处只是设置标记跳过 release，没有调用 quarantine 或写等价的保护状态。实际上传 + 实际 createPrismaBackend 的隔离复现：

1. 受控 worker 替身终止不结算，没有 exit 事件；上传返回 503/STOP_UNCONFIRMED。
2. 租约仍为 ACTIVE，平台 active=1。
3. 调用当前过期回收，推进到到期宽限后，租约改为 EXPIRED，active=0，仍未见 exit。

这说明“不立即释放”仍会经现有 TTL 路径释放未知后台占用。使用的是受控生命周期替身、隔离持久化算法，不是真实残留线程/OOM或生产 MySQL测量。证据：handler-evidence.json。

与此同时，text-extract.ts:542 仍 await workerPromise。假OCR recognize永不结算、terminate已结算时，根deadline30ms、内部10ms，推进100ms仍不结束；旧node:test同场景实测8000ms超时。初始化晚到与迟到停止的恢复仍未完成。

独立提取把未知停止状态写QUARANTINED，但迟到exit后无回收接线；release仅ACTIVE，sweep也仅ACTIVE。对应受控状态机验证仍为active=1、下一次PARSE_BUSY。它与Studio误回收是同一原停止/回收协议的两端问题，不能只保守留槽或只盲目释放。

要求不变：未知停止保留/隔离；停止证据成立后才幂等回收；创建/识别/终止/确认整体有界；恢复提交失败可重试。存储对象清理与线程退出分别核验，不能相互代替。

## 1. J-RELEASE / P1：物理对象仍在，额度已经释放

storage-quota.ts:425 的事务函数删除文档并立即扣减 storageUsed；Studio 在事务提交后才调用 deleteAssetFile（例如 handler.ts:4929）。物理失败后只补写 PENDING_CLEANUP 记录，新增上传的额度判断并未包含这部分物理占用。

**独立真实入口复现：限额 30、占用 30，私密文件删除遇到 EACCES，接口返回 200 + success=true / STORAGE_CLEANUP_PENDING，storageUsed 已变 0；随后再上传 30 字节成功。最终物理对象共 60 字节，额度仍只有 30。**

这违反原 F13“失败文件保留占用、不能因删除失败不断扩大资源”的要求。操作线索存在不等于成本已被计量，不能以新“DB 先行、物理后行”契约改掉原来的容量不变量。

再注入待清理记录创建失败：persistOrphanCleanupLead 捕获错误仅打印日志，接口仍返回成功/待清理；文档和额度已消失，文件还在，操作记录为空。必须在破坏性提交前保证恢复与计量事实可持久保留，不能事后尽力补日志。

### 共享引用还存在别名缺口

事务内按 `filePath === fp` 统计引用，但物理路径和唯一对象规范化允许 `assets/w1/shared` 与 `w1/shared` 指向同一对象。独立实际 remove_asset：删前者后，后者文档还在，物理对象却消失，用量变 0。正常“完全相同字符串路径”的共享保护已经通过，剩余只是同一已知对象的别名要使用一致身份判断，不扩展成新去重产品功能。

### 用户结果还需与清理状态对齐

批量硬删除返回 cleanupPendingIds，但回调未使用；批量移除甚至没有把物理失败放入失败/待清理结果，仍统计成功。独立运行两个真实后端，再将实际响应交给真实前端回调，均只显示成功。原列表筛选与 HTTP 错误已经修复，不需要重新设计页面；只在对应删除结果中呈现尚未清理和占用处理事实。证据位于 handler-verification.json 和 ui-verification.json。

## 2. J-UPLOAD / P1：保留容量有改善，仍缺真实恢复状态

### 未知保存标记分支不可达

普通上传在 `saved = await saveAssetFile(...)` 之后才设置 saveAttempted=true（handler.ts:4586—4587）；附件的 attSaveAttempted 同样在保存成功之后设置。当保存先产生文件后抛错时，标志仍为 false，`saveAttempted && !saved.filePath` 分支不会进入。

两条实际入口均复现：500，没有 STORAGE_OP_PENDING，文件与预留保留，这是较上轮盲目释放的改善；但操作仍为 RESERVED、filePath 为空，错误响应未给出稳定恢复状态。file-store 仍在内部随机生成对象名，外部写入前没有把目标定位绑定到操作；只凭这条 opId 无法定位具体未知对象。

### 已释放却仍被当成在途

普通 document.create 失败后文件和容量可清理，但 storageoperation 仍为 RESERVED。独立对账显示用量 0、reservedBytes=3，状态关系不成立。成功释放未形成相应终态，重放/恢复可能继续依赖过期“活动状态”。需补实际状态转换，不再加一层仅供展示的标志。

### 确认失败与元数据清理失败

确认失败时 handler 用 `document.delete(...).catch(() => {})` 吞掉清理错误，再删除文件、释放额度。独立故障组合：接口 500，但 APPROVED 文档仍在、物理对象已无、占用为 0。必须保留或标记可恢复状态，不能留下成功资料外观。

### 结构就绪和身份冲突仍有遗漏

- delegate 不存在时，findStorageOp 在操作前直接访问 undefined.findUnique；实际上传仍返回 TypeError 对应的普通 500，而不是原要求的 503/稳定 code。副作用为 0，但错误与部署门槛不诚实。
- P2002 分支只核对 workspaceId/bytes，没有复用正常重放分支的 userId 和状态核验。夹具在查找与创建间注入另一操作者已提交记录，当前调用仍 deduped=true；此为函数冲突分支验证，不声称真实 MySQL 调度或公网可利用。

## 3. J-CLEAR / P1：条件删行后释放失败仍丢恢复依据

clear-data/route.ts:128 条件删除记录后，第 133 行独立调用 releaseStorageBytes，两者不是同一提交，也没有在此前持久认领恢复状态。

独立实际 clear-data：文件已删除、文档条件删除成功，随后额度写故障，接口 500；占用仍为 30、文档和文件均无、没有本次操作记录。对于无历史操作记录的既有资料，该流程缺少可重放完成的对象级依据；反复执行 clear-data 也不会再扫描到此项。不能仅以 count=1 避免重复调用代替提交失败恢复。

已经通过并冻结：物理删除失败会保留文档和用量；扫描后真实新上传会完整保留。

另一个结果说明问题：两份文档共享同一个文件时，本次逐条都因“另一引用存在”跳过，sharedRefKept=2，记录和文件都还在，但 hasPartialFailure 不包含共享保留，message 仍为“纯净出厂状态”。应按实际清理/保留状态提示，不要求改变其他任务、组件、审计重置策略。

## 3. 必须修复的问题

### J3-01 / P1：恢复扫描绕开共享引用保护，删除仍使用的文件并释放占用

位置：src/app/api/workspace/clear-data/route.ts:114–123。清空的历史认领恢复循环直接执行 deleteAssetFile/finalizeObjectCleanup；共享引用检查在后面的逐文档循环才发生。

独立复现 `recovery-shared-defect`：用量和限额均 30；同一对象有 `assets/w1/x.bin`、`w1/x.bin` 两条资料；另有先前删除失败留下的 PENDING_CLEANUP RELEASE 认领。清空返回 200、sharedRefKept=2，但物理文件已消失，storageUsed=0，两条资料仍在。提示声称共享保留，而文件已经被恢复循环删除。

影响：资料不可读，仍被引用的容量错误释放，后续上传可使用错误腾出的额度。原提示词 §一.5、§三已经要求保护这些引用；属于同一范围的遗漏。

### J3-02 / P1：并发后到者关闭的是双方共用的认领，先到者无法终结

位置：src/app/api/studio/handler.ts:5002–5010；同类分支在 5858、6016、6127；src/lib/storage-quota.ts:555–559。

独立复现 `concurrent-cancellation-defect`：A/B 都读取同一资料、共用同一个确定性认领；A 删除文件与资料后暂停；B 的条件删行返回 0，于是把共用认领改成 CANCELLED；A 再执行终结，CAS 失败，返回 500。B 返回 404。最终文件和资料均无，storageUsed=30，认领为 CANCELLED。再执行清空不恢复此认领，反而提示纯净出厂状态。

该夹具只在文件删除和非事务删行后的确定位置加屏障；两个终结事务没有并发执行，因此结论不依赖内存夹具模拟数据库行锁。数据库真实事务不能修复已经在事务外被另一请求 CANCELLED 的状态。

影响：用户容量长期卡住，恢复扫描失去待处理入口。不能把“没重复扣减”当作已经满足“最终恰好释放一次”。对应原 §一.4、§三。

### J3-03 / P1：认领字节冲突不校验，终结采用调用方字节；未知大小被变成零

位置：src/lib/storage-quota.ts:453–485、508–530；handler.ts:4978、5010 等调用点。

两条独立复现：

- `claim-bytes-mismatch-defect`：现存认领 bytes=30，待删文档 fileSize=50；另有 50 字节对象，初始准确总占用 80。删除没有拒绝冲突，按调用方的 50 扣减，最终 used=30，剩余物理对象仍为 50。另一个对象的容量被错误释放 20。
- `unknown-size-defect`：历史物理文件 30 字节，fileSize=null，used=30；代码把 null 当 0，删除文件和文档、返回成功、认领 RELEASED，但 used 仍为 30。未知事实被伪装成已终结。

影响：前者出现计量不足，后者出现无法解释的占用；破坏性动作后再“人工核对”已来不及保护原始资料。原 §一.5 已明确要求“历史未知/大小冲突先保留并报告”。零字节真实文件仍需正常支持，不能与 null 混为一谈。

### J3-04 / P2：清空恢复段失败被吞掉，返回完整出厂重置成功

位置：src/app/api/workspace/clear-data/route.ts:125–128、211–226。

独立复现 `recovery-error-hidden-defect`：上次文件/文档均已删，但 30 字节认领尚待终结；本次终结事务提交失败。catch 执行 `pendingStill += 0`，返回 200、“纯净出厂状态”、pendingStill=0；实际认领仍 PENDING_CLEANUP、used=30。

影响：用户和管理员看到错误完成状态，无法得知清理失败。不能仅把 `+=0` 改成 `+=1`：还需覆盖待处理列表查询失败、循环中途失败、后续未处理项，返回真实状态。对应原 §三“不因异常假报完全成功”。

### J3-05 / P2：单项删除提交失败后，同一删除重试绕过恢复并报成功

位置：src/app/api/studio/handler.ts:4847–4850、5002–5010。

独立复现 `remove-retry-defect`：物理文件和资料已删、最终事务提交失败，第一笔返回 500，认领 PENDING_CLEANUP，used=30；用户重试相同 remove_asset，因文档已不存在直接返回 success=true/200，用量仍为 30，认领仍待处理。

影响：同一操作没有完成恢复闭环；不能要求用户为了释放一份文件的占用而清空整个空间。原 §一.4 的提交失败/重试要求尚未满足。恢复时仍须按持久化主体、空间、文档身份核权，不接受客户端提供路径作为授权依据。

### J3-06 / P2：普通与 P2002 重放共用校验仍漏 opType

位置：src/lib/storage-quota.ts:244–249、普通重放与 P2002 调用点。

独立复现 `reserve-type-defect` 和 `reserve-p2002-type-defect`：已有操作是 RELEASE/PENDING_CLEANUP，空间/用户/字节相同；普通预留和实际触发 P2002 的并发分支都返回 deduped=true。后一条预留事务已回滚，used=0，却声称已去重预留。

目前上传入口使用服务端随机 opId，因此此处**不能直接推断为客户端可利用的免费上传漏洞**；但服务契约与原 §二.6 明确要求的操作类型校验未完成。需要补齐这一个字段并真实覆盖 P2002，而非用普通重复请求冒充竞争分支。

### J3-07 / P2：缺列 P2022 不转换为既定 503/NOT_READY

位置：src/lib/storage-quota.ts:133–146、341–350，相关存储操作就绪错误转换处。

独立复现 `missing-column-defect`：storageoperation 读取抛出 Prisma P2022；实际 upload_doc 返回普通 500，无稳定 code，而不是约定的 503 STORAGE_QUOTA_NOT_READY。当前复现没有文件或计量副作用；不夸称已经导致数据破坏。

缺 delegate 已修好，但“表/列未就绪”尚未全覆盖。原 §二.5 已明确包含缺列；业务请求中不得生成客户端、建表或迁移。

## 4. 为什么正式测试全绿仍不能放行

当前正式 J3 的“交错”用例实际是清空完成后再删除，未让两个请求同时持有旧文档；标作 P2002 的用例走普通已存在查询；共享保留用例没有历史待清理认领；提交故障只验证了首次终结失败、第二次成功，没有验证第二次恢复自身又失败；没有大小冲突/null 与缺列用例。独立复现补的都是原验收场景，没有追加 F14 或商业功能。

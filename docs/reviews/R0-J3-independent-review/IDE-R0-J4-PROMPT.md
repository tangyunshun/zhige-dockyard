## 三、J3-01：恢复流程也必须保护实际共享引用

现状：clear-data 恢复循环先 deleteAssetFile，再检查后面文档列表的引用。出现 pending RELEASE + 两个别名引用时，文件被删、容量归零、资料仍在。

要求：

1. 主删除与历史认领恢复遵守同一对象身份和引用规则。每次准备外部删除时，根据当前持久事实核对规范对象、授权空间、关联文档、仍保留的引用，不能拿“有一条 PENDING_CLEANUP”当删除授权。
2. 对认领关联的待删文档与其他在用引用作明确区分：本次安全范围外的引用、扫描后新增的引用、按现行规则保留的共享资料，均须保留文件和计量。不因它们恰好同属本空间就删除。
3. 发现共享/未知归属时返回明确保留/待核实结果；不释放占用、不把操作标 RELEASED。不得让恢复阶段先删除、后续循环再谎称文件仍保留。
4. 如果对象确实无其他在用引用，恢复可以继续完成已授权清理；不能简单禁止所有 pending 以致失去恢复能力。文件 IO 仍在短数据库事务之外，不建通用任务队列。

验收：沿用 `recovery-shared-defect` 的前置数据，修复后两个资料、文件、30 字节用量均保留，响应说明共享保留；同空间无引用的失败认领可正常重试完成。

## 四、J3-02：共用认领不能被并发后到者取消

现状：同对象 A/B 共用 deterministic opId，A 删行成功、未终结；B count=0 就把 A/B 共用操作改 CANCELLED，A 终结失败。

要求：

1. `deleteMany.count=0` 只能证明本请求没有删到文档，不能证明整个对象清理已终结、没有用量待释放。禁止据此无条件关闭共用认领。
2. 主删除、治理记录物理删除、两个批量删除、clear-data 中受影响调用保持一致。可以利用现有持久状态、短事务和条件转换实现最小修复；若用归属/执行身份，其持久事实和校验必须确实成立，不能仅加一个进程内锁。
3. 终结必须在受保护事务中核对同一 workspace/opType/object/状态/可信字节，再只扣减一次并提交终态。已 RELEASED 的重放先识别终态，不能因为现用量不足而误判本操作发生新漂移。不得靠计量清零处理历史差异。
4. 终结之前出现异常，保留可重试事实；不能以 CANCELLED 隐藏实际尚未释放的占用。正常共享保留与取消语义若仍需要，必须与真实保留对象/用量一致。
5. 不把慢物理 IO 放入数据库事务，不更换数据库，不引入跨进程锁服务。

必须使用明确屏障复现：A/B 均已读旧文档，A 删行后暂停，B count=0，随后 A 终结。修复后最终文件/文档无、净用量0、同对象只释放一次、终态准确；另一文件/空间占用不动。补删除与清空交错、重复终结后余额已0、终结提交故障后重试。不能用“先完整清空、再调用删除”冒充并发。

## 五、J3-03：持久认领是可信事实，字节未知/冲突先阻断

现状：已有认领 bytes=30，调用方文档 fileSize=50，仍按50扣减；null 通过 `??0` 被当作真实零字节。

要求：

1. 在任何文件删除/最后元数据删除之前校验历史大小事实；fileSize=null、负数、非法值与真实0分开处理。未知/矛盾先保留文件、资料、占用，返回稳定待核实原因，不自动改历史数据。
2. 已有认领的空间、类型、规范对象、可信字节与本次操作一致，才能恢复。冲突时不复用为成功，不覆盖已有字节，不按较大/较小值猜测释放，也不声称已清理。
3. 终结时从受保护的持久事实确定应释放量，调用方快照不能任意覆盖认领量。认领重开也要核对事实，不能只改状态掩盖载荷变化。
4. 保留真实0字节文件、JSON纯文本、大小写对象身份、S3/本地同键契约。不增加真实文件扫描、迁移、批量修历史或去重产品。

验收：30/50冲突用例不得删除原文件，也不得释放另一对象的20字节；null用例保留并待核实；真实0字节仍能正常上传/删除，终态与计量一致；两条无冲突正常对象只释放各自真实字节。

## 六、J3-04：恢复查询或处理失败必须如实计入结果

现状：clear-data 的恢复 catch 只打日志、`pendingStill += 0`，导致待处理仍在却返回“纯净出厂状态”。

要求：

1. 查询 pending 失败、某条物理删除失败、终结/提交失败、循环中途异常及未处理剩余项，都有可诊断结果。已知数量就按实际记录报告；查询失败无法确认数量，明确“恢复检查失败/状态未知”，不要编造计数。
2. 根据实际成功/保留/失败/未知情况返回现有 API 的诚实状态和说明。存在任何未完成或未能确认项就不能声称完全出厂重置；是否使用非2xx或既有部分成功契约应与实际调用方兼容。
3. 不单纯把 `+=0` 改为 `+=1`；不能丢失循环中已成功与尚未处理的事实。允许逐项继续或安全中止，但不能吞异常后报完整成功。
4. 正常无残留清空仍按原流程完成；不要顺便修改非存储重置逻辑。

验收：无文档但有30字节待终结认领，连续两次注入终结提交失败时，每次都明确未完成、used=30、可恢复；故障解除后释放一次并终结。另测 pending 查询失败和处理多条时中途异常。

## 七、J3-05：文档已删后，相同删除重试仍须识别恢复状态

现状：单项删除最终提交失败后，文档已无，再调用 remove_asset 直接200成功，pending/占用原样卡住。

要求：

1. 根据持久化的 documentId、空间、操作者和清理事实识别该操作；文档不存在不能自动等同于清理完成。既无待处理事实且原本不存在的安全幂等行为保持。
2. 在既有删除链路或现有可复用的有授权恢复路径中完成同一对象重试；不要求用户重置整个空间。不能新建一个未接 UI/入口的“可恢复服务”交差。
3. 恢复失败返回稳定 code/opId/待处理事实；恢复完成后仅释放一次。API 不接受任意客户端 filePath/key 作为依据，不越过其他用户私密资料权限，不因文档缺失放宽身份检查。
4. 批量或治理删除若受同类提交窗口影响，采用同一协议保持结果真实；本轮只修受影响路径，不重做所有路由。

验收：先注入删除终结提交失败，然后重试同一删除（不清空空间），最终 used=0/RELEASED，另一资料与另一空间完整；连续重试不再扣减。另一用户/空间伪造 documentId/opId 不可触发恢复删除或释放。

## 八、J3-06：预留重放必须包含操作类型核验

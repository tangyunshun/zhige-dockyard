## 3. J3-02剩余 / P2：并发终结读到旧状态后，把已完成认领误报漂移

位置：`src/lib/storage-quota.ts:549`、553、569–574、590；实际表现经过`remove_asset`文档缺失恢复入口。

本轮已修好的是“第二次开始读取时，第一笔已经RELEASED”的顺序重放。但初始SELECT不排他；两个事务都读到PENDING后，第二个仍可能在扣量阶段看到第一笔已释放后的用量0。

独立复现 `overlapping-finalizers-characterization`：

1. d1文档已无，存在其30字节RELEASE/PENDING_CLEANUP认领，文件在、used=30。
2. 同一已授权用户并发发起两次实际remove_asset恢复请求。A/B的终结事务都先读到PENDING；在扣量前用显式屏障控制顺序。
3. A完成物理清理与事务提交，返回200/pendingCleared=true；used=0，认领RELEASED。
4. B再执行条件扣量，count=0；代码在重新确认当前认领状态之前，返回drift=true。
5. 实际B返回500/STORAGE_RELEASE_DRIFT，文案声称“已保留占用与待清理认领，请人工核对”；真实用量为0、操作已RELEASED，无待清理需要人工完成。

影响：同一成功操作被另一个请求误报为故障，用户/管理员被要求处理不存在的漂移。净扣减仍只发生一次，**本条未复现重复释放或额外资源占用**。

修复目标：同认领的并发完成按持久化终态返回幂等结果；真实PENDING且用量不足时继续保留并报告漂移。不能简单把所有条件扣量失败都改成成功。原J3-02要求并发/幂等及已完成重放不误判，范围不增加。

## 4. J3-04剩余 / P2：pendingCount把失败分支计数当成待清理总量

位置：`src/app/api/workspace/clear-data/route.ts:123`–137、269–270。`pendingCountKnown`仅由查询是否报错决定，`pendingCount`却直接使用只在部分失败分支递增的pendingStill。

两条独立复现：

- `shared-pending-count-characterization`：两个资料以历史别名引用同一对象，有1条待清理认领。清空安全保留资料/文件/used30，认领仍PENDING_CLEANUP，但响应为pendingCountKnown=true、pendingCount=0。
- `drift-pending-count-characterization`：无文档、认领bytes30、used10（真实历史漂移）。终结正确阻断，认领仍PENDING_CLEANUP、used10保持；响应driftSkipped=1，却同样pendingCountKnown=true、pendingCount=0。

这里的安全保留本身通过，中文提示也没有宣称完全出厂完成；错误只在新增结构化“已确认待处理数量”。调用方会把仍需处理的认领读成已确认没有pending。

修复目标：明确并落实pendingCount的持久状态计数口径；共享保留、漂移保留等仍为PENDING的认领不能丢失。可保留pendingStill为本请求已知失败数，但不能用它冒充未完成认领总数。查询失败继续沿用null/unknown，不重新引入伪造0/1。原J3-04要求结构化事实准确，范围不增加。

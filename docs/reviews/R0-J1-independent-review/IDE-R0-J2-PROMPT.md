## 2. J-UPLOAD：先修阻断与绕过，再修完整生命周期

### 2.1 身份和模型契约

- 普通上传现在 `storageOpId=""` 后没有赋值，必须修正；物理上传的操作 ID 非空、唯一且实际绑定本次已授权请求。不能只修一个赋值而保留其他协议漏洞。
- 同 ID 重放必须验证相同空间、操作者、字节、操作类型与允许的状态，按事实返回原结果/处理中/冲突；跨空间、不同载荷或已释放状态不得直接 dedup 后继续创建新对象。
- 记录 userId 使用服务端身份，不能写空字符串。对象位置应在外部写入前可追踪，不能先由 saveAssetFile 私自随机一个键，出错后只留下无法找到对象的 opId。
- storageoperation.id 当前为无默认值的必填字段，创建时未提供；修正 schema/创建契约。正式测试不能替无默认值字段自动补值掩盖错误。保持类型安全，不用 any 绕过数据库模型约束后称完成。
- delegate 未生成、表/列未迁移等结构未就绪，在任何额度增量或文件副作用之前稳定拒绝（503/明确 code），不得 TypeError→500 或先增加额度再报错。提交必要离线迁移/生成说明，不执行真实迁移/读库，不自动建表。

### 2.2 去重与预留原子提交

- 操作身份认领、容量写边界核验、预留记录必须形成同一受保护提交。当前先加用量再 create 操作，失败会留下无记录占用；P2002 不能在加量后直接吞掉。
- 两个相同 opId 并发，只能产生一次占用和一个已定义状态；失败或提交回滚不能留孤立增量。不同空间/不同操作互不影响。
- 不在数据库事务/锁中做慢文件 IO、解析或模型调用；通过持久状态衔接外部动作。0 字节物理文件仍可关联可恢复操作，但不增加容量，元信息保留 0。

### 2.3 两条真实上传全接线

- upload_doc 与 upload_knowledge_attachment 全部使用相同协议，实际覆盖保存、解析、document.create、确认、清理、释放和重启恢复。附件 document.create 仍在清理 try 之外，必须实际修改。
- 保存已产生字节后抛错/响应未知时，不得因 saved=null 就释放占用。保留持久待核实状态，并能利用预先记录的对象定位进行核实/恢复。
- 操作确认/待清理更新失败不能吞掉后返回完整成功；API 明确处理中或失败，并保留可恢复事实。文件已清理且容量已释放后，操作必须进入对应终态，不能一直 RESERVED。
- 正常保存的对象定位、真实文档 ID 和状态要持久对应；不能只在报告里写“已回填”。普通上传确认分支不能因空 ID 永远跳过，附件也必须完成确认。
- 保留 JSON 文本正常创建、单次解析/拒绝前不解析和父条目空间校验。对重复请求返回原结果或明确状态，不能跳过扣量后继续生成新物理文件。

## 3. J-RELEASE：实际入口接入原子状态，不能只新增函数

- remove_asset 私密硬删除、delete_removal_record、batch_delete_assets、batch_remove_assets 私密分支，以及清空文件段，全部接入同一安全删除协议。当前四个 Studio 分支仍调用旧的“释放后删记录”，没有调用新增事务函数。
- 新 `deleteDocumentsAndReleaseStorage` 也需修正：按真正状态转换成功的文档/对象决定释放，不能“总 count>0 就把全部输入 docs 求和”；使用最新受保护记录，不信任过期调用参数的 filePath/fileSize。
- 同文档并发、部分输入已被删除、删除与清空交错、提交失败/重试，都只能释放一次。物理文件已经确认删除但数据库提交失败时，保存可恢复状态，不能再被重放多扣量。
- 共享引用仍存在时不删除底层对象、不释放其仍被占用的空间；仅对本次数组去重不够。未知历史引用/大小有冲突时保留对象并报告，不扩展成新去重产品功能。
- 物理错误、额度差异、记录或提交错误沿真实 API 链路阻断或返回待处理，不得返回“删除成功”。保留已移除自动 SET 0 的改进；软删除不释放、恢复不重复加、文本不释放虚假字节。

## 4. J-CLEAR：这一项必须真正修改 clear-data

当前 clear-data 的起止哈希相同，仍是扫描后全 workspace 的 deleteMany。不要再仅在报告中宣称已改。

- 只删除本次安全认领并核实成功的记录；失败/待核实对象保留文件关联、状态和占用。
- 扫描后上传成功的新对象必须保留文件与文档，或新增上传在副作用前明确拒绝；禁止清空进程删掉该新文档。
- 与另一删除/清空操作竞争时同对象只提交一次释放。部分失败返回实际明细与状态，不假报全部完成。
- 保留既有空间权限、确认文本，以及非存储的任务/组件/默认初始化/审计策略，只修改本批文件与容量相关段和必要结果说明。

## 5. J-PARTIAL：修正两处过滤方向和 HTTP 错误处理

- handleBatchDeleteAssets 和 handleBatchRemoveAssets 当前 `filter(succeededIds.includes)` 恰好保留成功项；应只移除实际成功项，保留失败、跳过和无关条目，或刷新真实列表。
- 401/403/5xx/无效响应先按错误处理，不修改列表，不用“没有需要删除/成功移除”替代权限或服务错误。207/有效部分结果才按实际成功集合更新。
- 后端保留可核对的 succeededIds/failed/skipped 和数量，客户端不能在缺集合时不顾跳过项直接把所有请求 ID 当成功。
- 两处都验证初始“成功、失败、无关”三类条目，以及全成功、部分成功、全失败和权限拒绝；不再只跑与本回调无关的旧页面脚本作证。

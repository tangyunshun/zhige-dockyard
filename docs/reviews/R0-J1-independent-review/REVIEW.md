## P1：J-UPLOAD 的实际入口与持久化协议不成立

### 空操作 ID 可绕过另一空间的额度

handler.ts:4512 初始化 `let storageOpId = ""` 后未赋值；4580 将它传给 reserveStorageBytes。storage-quota.ts:209 只要找到相同 opId 的记录就返回 deduped=true，不核对 workspace、操作者、字节、状态；handler 也没有根据去重状态恢复原操作，而是继续保存新文件。记录 userId 被写为空字符串，filePath 又没有预先持久关联。

独立真实 handler 夹具：空间 w1 上传 3 字节成功；随后向空间 w2（storageLimit=0）再上传 3 字节，仍返回 200，w2 用量为 0，物理文件和文档已经产生。唯一操作记录是 w1 的空 opId。该风险在允许操作插入的模型夹具中隔离验证；下述主键错误是另一独立阻断问题，不能用它掩盖空 ID 的风险，也不能据此声称线上已经被绕过。

### 模型主键缺失、增量与操作写入分离

schema.prisma:2139 的 storageoperation.id 是必填 String @id，没有默认值；createStorageOp 的数据及 228、239 行调用均未提供 id。正式内存夹具自动为任何缺 id 的记录补随机值，遮蔽此约束。

按实际 schema 必填约束的独立夹具拒绝操作插入后，用量已增加 30，操作记录为空。普通操作插入故障同样留下此差异，因为 UPDATE 和 create 不在同一提交中。测试只验证了模型契约，不连接真实 Prisma/数据库。新客户端未生成、delegate 不存在时，当前错误是 TypeError→500，而非报告承诺的 503 未就绪。

即使补齐主键，两个相同 opId 并发调用也会先各增加 30，再发生唯一冲突；createStorageOp 吞掉 P2002，两个请求均成功，用量 60，只有一条记录。串行 findUnique 去重不是并发原子去重。

### 失败、确认和恢复仍未接全

- 普通 doc.create 失败会清理文件并释放字节，这是改进；但操作状态仍为 RESERVED，没有转为已释放/失败终态。
- 附件 document.create（handler.ts:6532）仍位于保存 try 之外；实际注入故障后留一个 3 字节文件、3 字节占用，操作无对象定位。
- 保存先产生字节后报错，仍通过 saved=null 分支释放字节，留下对象且用量 0。未按报告所称转 PENDING_CLEANUP。
- confirmStorageOperation 捕获并吞掉操作更新失败，夹具中调用正常返回而状态仍 RESERVED；不能据此宣布确认完成。
- 普通上传空 opId 还使 `if (isMultipart && storageOpId && saved)` 确认分支永远跳过；附件也没有完成对应确认调用。
- file-store 自行生成对象 UUID，外部写入前没有可持久定位目标；响应里的 opId 不能让重启后的恢复自动找到该对象。
- 0 字节文件仍经 `fileSize > 0 ? ... : null` 归一为未知，报告称“保留 0”与当前实现不一致（静态核查）。

以上直接对应上轮 B 部分，不要求新增通用恢复系统。

## P1：J-RELEASE 新函数存在，但实际删除没有使用

storage-quota.ts:344 新增 deleteDocumentsAndReleaseStorage；Studio 仍在 4888、5699、5834、5905 调用旧的 releaseStorageForDeletedDocuments，再独立删记录。没有调用新事务函数。

实际 remove_asset 并发删除同一份 30 字节文件，用量 100 最终仍为 40；另一份 70 字节文件还在。一条请求 200，另一条 500，重复释放不可撤回。

新函数本身也不能直接接线了事：逐个 deleteMany 后，只要总 count>0 就按全部传入 docs 求和。输入包含已不存在的 30 字节文档和实际删到的 40 字节文档时，用量 100 被减至 30，而只应减 40。必须按实际状态转换成功的对象和最新引用事实决定释放。

另一个实际 handler 场景：两份文档引用同一对象，删除其中一份即删掉文件并释放全部占用，另一份文档还在却不能再读取。原 C 部分已经明确要求保留仍被引用的对象，不能仅在本次输入数组中去重。

旧自动 SET 0 已移除，这是通过的子项；仍需让差异/提交失败沿实际调用链阻断，不假报成功。

## P2：J-PARTIAL 两处回调发生反向筛选

WorkspaceInternalLayoutV3.tsx:3492、3696 附近均为 `prev.filter(a => succeededIds.includes(a.id))`，它保留成功项，移除失败、跳过和无关项，逻辑正好相反。

执行实际两个回调，初始条目 deleted、failed、unrelated：正常/部分成功响应含 succeededIds=[deleted] 后只剩 deleted；403 响应没有成功 ID 时整个列表变空，且没有按 HTTP 错误处理。共六条场景保存于 ui-verification.json。后台数据未因前端筛选改变，但用户看到的资料列表和提示不可信，不能据此交付用户流程。

## 原边界要求的剩余子项

### J-KEYS（P2）

独立假 SDK 验证 S3 PUT/GET/DELETE 同键，本地只有一个历史位置的读删也通过。但两个已知候选同时存在时，当前函数删第一个就返回成功，仍留另一个，未报告歧义。`w1/../../outside.txt` 这种内部路径穿越也未被根目录校验拦截，实际 helper 的内存 fs 验证访问到了 assets 根之外的合成对象。此为函数契约/历史路径防护验证，未证明公网 API 可利用、未访问真实用户文件。原 F 部分已要求限制根/空间以及歧义诚实阻断。

### J-WRITE-BOUND（P1）

实际读 -1 后在 SQL 执行前改为 0，现在会拒绝，通过。但两条 UPDATE 均未包含有效用量保护：读后 used 从 0 变为 -10，预留 5 的写入通过，最终 -5；仍不符合上轮 G 部分明确的读后非法用量拒绝。

### J-RECONCILE（P2）

1. normalizeObjectKeyForDedup 无条件 toLowerCase，将大小写敏感存储中的 A.txt 与 a.txt 合并。两个各 30 的独立对象报告为一个 30 字节对象。
2. 文档集合为空但用量为 30 时，usageDrift 为 null，不能发现无文档占用差异。
3. 只提供 listObjects 时函数不调用它，只有额外传 fileExists 才使用清单；coverage 却称 objectListProvided=true。独立清单应能作为已提供事实参与核查。
4. 预留、确认、待清理只统计数量，未完成数量关系又受实际入口不更新状态影响，不能以这些计数证明计量已闭合。修复应与持久操作事实一致，不建立新运维平台。

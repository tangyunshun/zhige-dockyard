## 问题与影响

### B2-1 / P1：截止时间仍只在事务前判断，等待后跨过截止仍可履约

证据位置：`src/lib/payment/seat-addon-fulfill.ts:76`、`:157`、`:202`、`:210`、`:245`。

订单期限在预检时检查；取得履约权的 updateMany 条件只有 id/PENDING。套餐期限也只在事务前与 Date.now 比较；事务内核对类型、状态、数字，以及写入时的到期日期“与原报价相等”，没有再次确认该日期仍有效。

独立验证使用实际服务及三个实际入口，只推进隔离时钟、不等待真实时间：

1. 初始订单还有 500ms 有效，所有预检通过。
2. 在实际事务回调开始前推进时钟 2 秒，模拟数据库排队/请求耗时。
3. 订单仍为 PENDING，没有清扫器竞争；共享服务、REAL 外层、MOCK POST 均将其履约为 SUCCESS，增加 2 席位。
4. 套餐还有 500ms 有效，事务开始前或条件席位写入前跨过期限，同样 FULFILLED。

这是“取得履约权之前已经过期仍被放行”，不是要求截止前合法取得履约权的事务必须在截止前完成提交。需明确合法裁决时刻，并在相应事务/写边界核验时间；不能再只增加一次事务外检查。无需在本批决定迟到付款退款政策。

验证 JSON 的 `observations` 保存 5 个案例、实际写条件、当前时间与两类期限。该模型不证明线上发生过此竞争，也不证明实际 MySQL 锁行为。

### B2-2 / P1：下单和履约的周期规则不一致，生成可付款但无法履约的新订单

证据位置：`src/app/api/workspace/seat-addon/route.ts:82`、`:87`、`:96`、`:105`、`:124`；`src/lib/payment/seat-addon-fulfill.ts:172`。数据库 `workspace.planBillingCycle` 是可空 String，注释约定 MONTH/YEAR，不是枚举约束。

下单端把非 YEAR 的任何值按 30 天计算，直接把原值写入 metadata。履约端新增了“周期必须非空”的要求，却没有把同一规则前移到收费入口。

独立组合执行的是实际下单 POST → 网关 IO 夹具 → 实际本人订单 GET → 实际共享履约：

| 空间原始周期 | 下单结果 | 本人查询二维码 | 付款确认时结果 |
| --- | --- | --- | --- |
| MONTH | 200 + payUrl | 有 | 正常发放 |
| null | 200 + payUrl | 有 | 拒绝，缺 billingCycle；订单 PENDING |
| 空字符串 | 200 + payUrl | 有 | 拒绝，缺 billingCycle；订单 PENDING |
| WEEK | 200 + payUrl | 有 | 被当成月付报价且正常发放 |

因此，缺字段不是只有历史坏订单才会遇到，当前下单逻辑本身能继续制造此类新订单。若接真实收款，将产生付款后不能自动取得席位的风险与人工处理成本。非法周期按月处理还引入未批准的报价解释。

应在创建订单和调用网关前核验真实周期为 MONTH/YEAR；履约端独立核验同一合法集合。缺失/非法时明确阻断，不补成 MONTH、不清洗历史库、不改月年价格公式。未查询真实数据库，因此不声称当前存在多少此类空间或真实损失。

### B2-3 / P2：模拟收银台漏了“打开成功订单”和“重复确认成功”的完整结果

证据位置：`src/app/user/pay/mock/page.tsx:80`、`:103`、`:195`、`:245`。

- 首次查询 SUCCESS：effect 仅为非成功终态设置 result，SUCCESS 没有设置。实际组件显示状态行“已支付并入账”，但结果区仍渲染禁用的“模拟支付成功”按钮，缺席位完成结果和空间入口。不能说整页显示未支付；实际错误是状态行与结果区不一致。
- 重复确认：后端诚实返回 success:true/alreadyProcessed:true，前端设 order.status=SUCCESS，却把 result.tone 设 neutral。结果分支以 tone===success 决定是否完成，于是出现警示图标与通用账单/返回入口，缺少该商品的完成导航。

独立验证执行了真实 MockCashierInner、真实 effect、真实 authFetch、真实 JSX 分支；只替换 React hook/渲染 IO 与 fetch。验证 JSON 记录 SUCCESS 的 result=null、禁用支付按钮、无 Link，以及重复确认的 neutral 结果和只有通用账单 Link。不是只检查源码字符串。

应以可信订单状态/明确完成结果决定业务分支，颜色只负责表现。首次成功、重新打开/刷新、重复确认均显示商品对应的完成结果；保留“未重复入账”和 MOCK 非真实扣款说明。前端注释称“2xx 且 success”但当前未核验 res.success，补修时应同步确保明确业务成功才设本地 SUCCESS，不把任意 2xx 当成功。

原 EXPIRED/FAILED/REFUNDED 假成功已修复；真实扫码页的席位成功文案亦已修复。本轮真实 QR 组件受控状态渲染覆盖 6 种状态。以上不等于浏览器 DOM 或实际扫码验收。

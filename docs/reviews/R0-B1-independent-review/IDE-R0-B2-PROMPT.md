## 二、B2-1：把时间判断落实到明确的事务裁决边界

实际反例：预检时订单还有 500ms；事务开始前模拟等待 2s；共享服务、REAL 外层、MOCK 都仍 SUCCESS+2 席位。套餐在预检后过期也一样发放。

要求：

1. 明确订单可以取得履约权的时间点、有效比较方式和套餐仍可应用增量的条件，遵循当前“过期拒绝”规则；先检查真实 order-expiry helper 的边界语义，不自行变更商业政策。
2. 在合适的事务/锁/条件写边界重新核验真实订单期限和套餐有效性。事务外读、事务外 Date.now、只比较日期等于报价日期都不够；要考虑进入事务之前排队、获得可裁决边界之前等待、预检之后时间跨界。
3. 使用项目一致的时间口径；不混用 MySQL NOW() 与现有 JS Date 造成时区漂移。若设计依赖锁，说明锁顺序、读取语义和取得锁后的判断时刻；测试中不把普通 findUnique 伪称锁定当前事实。
4. 当前订单真实仍为 PENDING 且符合过期条件才可过期转换；条件竞争失败按最新状态分类。保留旧读过期请求不覆盖 SUCCESS 的有效修复。外层入口不得绕开席位最终裁决。
5. 已按规则取得履约权的正常事务，不因为完成提交时跨过时间就被后续请求覆盖成 EXPIRED。不要对已经有效发放的订单清账、撤回席位或自动退款。
6. 套餐基准变化、资格失效、写入失败时，订单状态、席位、履约 metadata 仍同一事务回滚。异常/未知提交结果不武断宣称一定 PENDING；原订单可查询/安全重试，不引导再付一遍。
7. 真实付款已发生但本地无法合法履约时，按已有拒绝/重试与人工核查边界诚实返回，保留可诊断证据。新增退款/宽限期/补差/后台恢复系统不在本批范围。

不能仅给 updateMany 加一个进入事务前算出的常量时间，就宣称解决了所有锁等待。说明选定的授权裁决边界及证据；本批不连接真实数据库证明锁。

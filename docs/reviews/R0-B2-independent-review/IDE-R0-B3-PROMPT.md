## 2. 已证实的根因，不能再重复的实现

当前代码：

```text
$transaction回调开始
  now = new Date()
  await 订单updateMany(expiresAt >= now)
  await 空间findUnique()
  await 空间updateMany(planExpiresAt > now)
```

进入回调不等于已经锁住订单和空间。任何后续await都可能等待；条件即使按最新行求值，参数now仍是旧时间。

本轮反例：08:00:00.000保存now；截止08:00:00.500；第一条写操作内部等2秒后才裁决；旧参数仍允许SUCCESS+2席位。套餐在事务内读取/写入等待中到期也会放行。

不要再仅把new Date移到另一个异步操作之前，不要只给where增加与同一旧now比较的条件，也不要把测试等待全部放在调用事务回调之前。报告不得声称“取锁等待一定发生在回调前”。

## 3. 最小修复原则与明确裁决点

选择与现有Prisma/MySQL模式匹配、可解释的事务实现，满足以下性质：

1. **在会影响资格的等待结束后、仍能保证完整回滚和互斥的边界，采样新时间并作最终授权判断。** 可以使用正确的行锁/当前事实读取后判断，或在已获得相关写锁且尚未提交时作最终核验；说明真实取得了什么锁、顺序是什么、时间何时采样，不能只用普通findUnique冒充锁。
2. 需要考虑订单行和目标空间行，两者都可能等待。只锁订单后马上采样时间、随后等待空间写入却复用旧时间，仍不能覆盖套餐场景。明确一次授权点；授权点之前的必要等待计入有效性判断。
3. 时间规则沿用order-expiry：订单过期定义now>expiresAt，等于期限不过期；历史null期限保留原语义。套餐沿用当前严格未到期规则。报价plan/cycle/expiry与可写企业资格、席位范围继续核对。
4. 订单SUCCESS、席位增量、履约metadata同一个tx。若先作事务内临时写再作最终核验，失败必须全部回滚，对外不能出现已成功但无权益；不要事务内根客户端写，不新增已提交中间态。
5. 授权通过后提交阶段才跨过期限，不要求反转合法授权，更不允许后续过期请求覆盖成功。相同订单并发仍仅一次发放。
6. 超时/资格失效应返回现有可诊断拒绝；仅实际仍PENDING且确实过期的订单可条件关闭，竞争失败按最新状态分类。不要新增退款、宽限、补差、重买或后台恢复政策。
7. 不混用MySQL NOW()和项目JS Date引入时区漂移。若使用SQL锁，参数必须绑定、表名按真实schema核实；不得将orderNo或workspaceId拼成SQL。IO只能在隔离测试中模拟，本批不连真实库。

先在定向测试里复现下表中当前未通过场景，再修改服务，使同一组测试通过。不要在失败后修改断言来接受错误履约。不要为此新增锁表、进程内互斥、缓存或新服务。

## C1 / P1：同一套餐改价或改权益后，仍可按旧的免费判定开通

证据：`src/app/api/workspace/upgrade/route.ts:183–202`，`src/lib/workspace-upgrade-service.ts:92–99,228,287–296`。

入口第一次严格读取配置，确认 STANDARD 月年价格都为 0；传给开通服务的仍然只有 key、周期、source，没有已核验价格/权益快照或免费授权凭据。服务第二次严格读取只要求“存在、启用、可购买、价格合法”，**合法收费价也会通过**，随后直接写企业类型、配额和 SUCCESS 账单。

独立执行真实 route + 真实套餐服务 + 真实 provision/upgrade 服务，模拟两次查询之间管理员修改配置：

1. 第一次：STANDARD，月/年均 0，成员上限 2。
2. 第二次：仍为 STANDARD，月 19900、年 199000，成员上限 99。
3. 实际：HTTP 200，`free:true`；空间成为 ENTERPRISE，上限 99；写 SUCCESS 账单金额 19900；支付调用 0。

这些金额/配额仅为测试夹具，不是项目真实售价。该漏洞需要两次读取之间发生配置变化；**没有证据证明当前线上发生了该事件**。但代码确实没有保护这个时序。稳定配置时不能据此声称任意用户可直接免费买 PRO。

即使价格仍 0，第二次只改变成员上限也会静默以新权益写入。此前要求“配置不一致安全停止/重新确认”没有实现。仅固定 key 不等于固定已批准的免费资格。

修复要求：服务端免费授权必须绑定规范目标和实际使用的价格/权益事实；进入任何写入前严格确认当前配置与已确认内容一致，免费分支始终只允许既有基础身份且月年均 0。实际写入不得再次读取宽松配置或用另一份配置覆盖。保留正常付费履约/管理员职责，不能把客户端 paid/free/source 当授权证明。

## C2 / P2：retain/delete 在配置最终拒绝前已经写库，依赖补偿清理

证据：`src/lib/workspace-upgrade-service.ts:367–407`。

两种方式先 workspace.create，再 workspacemember.create，随后才在 upgradePersonalToEnterprise 内执行第二次严格套餐核验。

独立反例：首次免费且启用，第二次停用。两种方式均最终返回 400，但已依次执行“建空间→建成员→删除成员→删除空间”。本轮 stub 中补偿成功，无残留、无账单、无资产迁移；**不能将其描述为已经造成线上孤儿或迁移丢失**。但它不满足既定的“核验失败前零业务写入”，真实补偿失败还需要额外处置。

修复要求：将本批套餐/免费授权核验置于建空间、建成员、额度/赠送与迁移之前；拒绝类请求不能依靠先写后删来满足零副作用。正常开通过程的其他运行故障恢复不在本批改造成全新分布式事务。

## C3 / P2：混合价格只阻断零价周期，正价周期仍下单

证据：`src/app/api/workspace/upgrade/route.ts:193–225`，现有组合测试仅测试月 0 年正的 MONTH 请求。

前一批要求将“基础档月0年正/年0月正”作为待确认配置拒绝，不能自行设计周期赠送。实际实现只在当前 cycleAmount<=0 时拒绝。同一个 STANDARD 月0年10000，选 YEAR 仍生成 10000 的 PENDING 并调用支付。

本反例**没有提前开通、没有真实扣款证据**；它是业务规则未完整实现，不等同于免费领取收费权益。补齐两个方向、两个周期的判定与测试；规则未批准时，不在这个批次自行解释为可售套餐。

## C4 / P2：两处弹窗仍把“success 且没 payUrl”当作已开通

证据：`src/components/studio/UpgradeModal.tsx:106–115`；`src/components/workspace-hub/modals/UpgradeModal.tsx:132–155`。

独立执行实际 handleUpgrade：响应 `{success:true, orderNo:"isolated-pending"}`、没有 payUrl/free，两个弹窗均提示升级成功、调用完成回调并关闭；中枢弹窗还写已升级存储标记。它们并未像独立升级页一样要求 `free===true` 才认定免费完成。

边界：当前网关成功返回按实现总带 payUrl；因此这是**缺失/异常响应下的防御与契约遗漏**，不是已证明正常网关会返回该形态，也不是后端实际授予权益的证据。有 payUrl 的普通待支付响应，本轮两个弹窗均正确跳转且不调用完成回调。

修复要求：明确区分真实免费完成、待支付和异常/处理中三种结果；无完成证据时不得触发已开通提示、标记和回调。增加页面行为验证，不能拿后端“缺目标返回400”的测试作为前端成功状态证据。

## C5 / P2：回归与交付报告仍缺少关键证据，回滚指令仍不安全

证据：`src/app/api/__tests__/r0a2-real-combo.test.ts:62–65,87–91,113–114,257–268`；`docs/reviews/R0-A2-fix-report.md:136`。

- 新增真实组合测试是有效改进，但套餐数据始终固定，未覆盖第二次变化；没有 delete 分支的真实组合测试；配额写只返回常量，没有存储最终配额供断言。不能据此声明所有写边界和最终配额已验证。
- “自助显式收费 PRO，直接调用底层服务→开通成功”的测试只证明服务能写入，不能证明已付款；低层函数可以信任受控调用者，但免费入口必须有明确的服务端授权事实，不能拿这条正向用例替代 C1 反例。
- 默认未知 Prisma 操作直接返回 null，可能掩盖新增副作用。应记录写操作、外部调用和最终数据；关键未实现 stub 应显式失败。
- 报告仍建议 `git restore` 10 个文件到 R0-A1。普通 git restore 恢复的是索引/指定提交，不能恢复未提交的上一批快照；当前多批与他人改动叠加，照做会丢修改。本轮没有执行。新报告须明确撤销这条建议，回滚仅基于事先保存的本批快照/最小补丁；没有快照就如实说明。
- getWorkspacePlanStrict 文案称“安全整数”，代码使用 Number.isInteger 而非 Number.isSafeInteger。正常 MySQL Int 价格行不具备超出 JS 安全整数的值，因此本项不是已证明正常库财务漏洞，但实现、测试与报告应一致。

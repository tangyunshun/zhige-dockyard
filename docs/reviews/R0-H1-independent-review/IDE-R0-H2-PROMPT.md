## 2. 最小方案与明确边界

- 不将128改成256/512或其它经验值作为本次修复；“更保守”不能代替“有适用依据”。
- 不要求证明所有供应商/分词器。只支持能从现有服务端事实核查的边界来源，对其适用模型/协议/请求做判断；其余付费请求明确拒绝。不要为了过验收新增任意填写“可信Token数”的后门。
- 可优先检查最终服务端模型执行计划中已有的真实硬上下文限制，使用完整、可靠的硬限制作为保守输入预算（允许偏保守，不用字符0.7之类比例缩小成本边界）；或者使用已有可信且明确适用的计量/封装约束。选择方案后说明来源、单位和适用条件。
- 注册表中的0、缺失、非法数值、默认猜测或无法确认适用的限制不能自动变成可靠来源；客户端传入的inputTokens/contextLimit/预算不能替代最终服务端计划。
- 如果现有事实不足以采用某种来源，先对该路径返回稳定未就绪错误，不编造配置、不读取真实库补数据、不花钱测供应商。缺哪些证据在报告说明，不扩成新产品。
- 字节计算/字符粗估可保留作诊断或辅助限制，但没有适用证据时不能标为“已证明上界”。若保留字节方案，必须同时有能覆盖当前模型/协议封装的可核查依据与失配拒绝，不能继续对所有协议通用套128。
- 用于准入的边界须与最终部署、最终提示词/材料、实际输出硬上限绑定。边界缺失/失配时在费用暴露前拒绝，不能先执行再从usage看是否超标。
- 维持至少一个具有明确可靠边界的正常付费模型对照；合法明确零供应商成本可按现有规则处理，但不能借免费标记绕过模型/输入/权限或未知附加费用检查。
- 来源/数值应能在既有返回对象或内部诊断中区分估算与准入依据；不记录原始材料、提示词、密钥，不新增持久化表或运营页面。

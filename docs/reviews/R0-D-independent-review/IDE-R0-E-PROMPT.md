## 2. 已证实的根因

payment-gateway.resolvePaymentMode当前先判断raw===mock即返回MOCK，再判断NODE_ENV；因此production显式mock绕过原来的缺配置保护。真实mock确认路由只看该函数返回值，因而可调用grantPoints等发放逻辑。

独立复现使用完全模拟NODE_ENV/PAYMENT_MODE，真实gateway+mock GET/POST+grantPoints：production+mock返回模拟收银台，POST200、钱包加100、订单SUCCESS。没有读取真实环境或调用外部渠道。

不得只改UI、不依靠开发人员记住生产配置、不在启动日志告警后继续发放，也不得新加一个可开启的生产mock豁免。

## 4. 服务端行为要求

### A. 统一模式裁决，显式生产mock必须拒绝

- NODE_ENV=production且PAYMENT_MODE经现有trim/大小写归一后为mock，抛出稳定可识别的配置错误，例如PRODUCTION_MOCK_PAYMENT_DISABLED；resolvePaymentMode及直接createCharge均不能返回可用MOCK/payUrl。
- 必须在任何实际网关调用、模拟入账、付费订单/收费权益业务写之前拒绝受影响路径。不能只改一种商品或只拦POST漏GET。
- **不得静默将production+mock改成REAL并调用真实供应商**，即使凭证看似齐全也拒绝该错误配置，避免意外真实下单。
- production显式real、未配置或原有未知值的安全行为按现有规则保持：不能降级MOCK；真实凭证不全则诚实拒绝。不要借机规定新的价格或商业默认值。
- 非生产环境的显式mock及既有缺配置联调行为保持；显式real不允许因缺凭证回退mock。
- 不新增ALLOW_PRODUCTION_MOCK之类开关、不按用户/管理员身份放开、不允许浏览器传mode覆盖。

### B. 模拟确认GET/POST双门禁

- production显式mock时两个方法都返回明确不可用响应，建议403 + success:false +稳定code及通俗error，不能被通用catch变成不明确的500。
- 在读取订单和进入任何发放分支前拒绝，充值/席位/套餐三类及历史PENDING MOCK订单均不得通过模拟确认变SUCCESS或授予权益。
- 保留既有模式先行门禁及可用联调模式下的登录/归属校验；拒绝响应不含订单、金额、用户、密钥或证书信息。
- 非生产模拟成功仍如实标注MOCK/非真实扣款，重复确认与席位一次性保持。不要修改幂等键、修改过去MOCK成功记录或把它们认成真实收入。

### C. 三条付费下单路径明确报错

- 充值、席位增购、付费套餐升级在创建本次PENDING付费订单及发放之前遇到该配置错误，应返回统一可诊断业务结果，例如503 + success:false +稳定code及“当前支付配置不允许在生产使用模拟支付，本次未完成下单”的说明。
- 不返回模拟payUrl、不调用真实渠道、不先改权益再报错、不自动换模式/重试另一渠道。不要因为通用catch吞掉新错误而只剩“服务器内部错误”。
- 仅处理这一配置错误；已批准的免费开通资格和正常非支付流程保持，不把生产付款闸门变成全站开通禁用。
- 其他真实渠道缺凭证的旧行为仅作必要回归，不顺手重写全站订单生命周期、取消、期限、QR载体或退款。

### D. 已付款事实与历史查询保持

- 可信真实notify仍经原验签与金额/订单规则履约，不因错误PAYMENT_MODE而丢弃已经实际收款的真实通知。不得让模式修复放宽验签或模拟通知为真。
- 普通本人订单查询/历史列表仍只读可查；不因停用生产模拟确认而删除历史、改metadata或把历史MOCK改REAL。
- 不对历史账做清账、补扣或自动退款；历史调查不在本批。

## 5. 页面可见交付

沿现有充值/席位/升级入口触发该错误时，应显示后端明确原因，不显示下单/支付/到账成功，不跳转模拟页，不自动重购。

生产直接打开模拟页时显示不可用，无可操作模拟付款按钮；不能因为403/503或业务失败而设本地SUCCESS。非生产正常联调的成功、失败及商品类型展示不退化。

优先用已有authFetch错误分支；不改变现有页面布局或新增系统设置界面，不读取/展示环境密钥。报告明确组件受控执行与真实浏览器验收的区别。

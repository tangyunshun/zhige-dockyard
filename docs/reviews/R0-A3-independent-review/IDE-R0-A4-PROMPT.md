## 2. D1优先：阻断危险的自助资产迁移方式

独立审核执行真实资产迁移后，在个人赠送迁移IO处注入失败，实际catch调用cleanupOrphan删除目标空间，资产引用没有恢复。这是现有失败分支问题，不能把资产已迁入的目标当空壳删除。

本批采用最小止血方案，避免仓促改造跨资产/账务事务：

1. 自助升级的option=delete暂不可用，后端在创建任何订单、支付、空间、成员、额度、账单、赠送或资产迁移之前明确拒绝，提供稳定错误码及中文说明。不能仅靠前端禁用。
2. 三个用户入口诚实展示迁移方式暂不可用及原因，保留原地升级/并行保留可用；不要声称已有数据迁移成功。若某页面本来没有delete选项，不要凭空新增。
3. 枚举该方式的其他实际调用者（包括历史待支付/付款后履约、管理员/签约），明确安全策略。不要让服务层已有通路绕过保护继续执行危险迁移；不要把管理员权限视为可接受数据丢失的理由。
4. 已存在订单不得擅自标成功、退款、改金额或删除。对历史/受控付款后迁移调用，如果当前无法安全完成，应在任何资产写入前明确拒绝并记录可诊断错误，报告人工恢复/后续专项需要。不能把失败伪装已履约；不能暗中增加新补账/恢复表。
5. 本批不要以“只删掉cleanupOrphan”代替完整恢复设计，也不要实现未经授权的全资产迁移或账务补偿。恢复迁移功能需后续独立批次覆盖资产、赠送、归档、重试/恢复、历史订单；本批先确保它不可触发危险写入。
6. 原地升级upgrade与并行创建retain保留既有正确语义、权限和付费/免费边界。新建空壳在资产未迁入时的已有恢复不必无关重构。

用户可见交付：迁移选项显示不可用，说明稍后开放；其他安全方式可继续；失败保留当前选择/材料，不发生资产移动或收费订单。

## 4. D3：明确页面完成协议，并补真实回归

独立页现只看HTTP，HTTP200且success:false/free:true仍会标成功。三个入口对free:true但缺返回空间也未做完整判断。

统一三个调用者：

- HTTP失败、网络失败、success不是明确true：失败/错误状态，message优先，保留选择；不得写true成功标记、触发完成回调或跳转为已开通。
- success:true且有效待支付信息/payUrl：待支付/收银台，无开通成功标记和回调。
- success:true、free:true且API约定的有效workspaceId等完成证据齐备：才按已开通更新本地状态、刷新或回调。
- success:true但缺payUrl/free/完成证据，或协议自相矛盾：待处理/协议错误，不能当成功，不自动重试下单。

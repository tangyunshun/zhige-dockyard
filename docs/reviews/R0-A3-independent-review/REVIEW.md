## D1 / P1：迁移资产后仍无条件执行“孤儿空间”删除

位置：`src/lib/workspace-upgrade-service.ts:375–380,419–440,454–480`。

迁移方式执行顺序：新建空间/成员 → 开通并写0元SUCCESS记录 → 资产迁移事务提交 → 个人赠送额度迁移 → 原空间归档。任何后续异常都会进入同一个catch，并调用cleanupOrphan删除新空间及其成员。

**资产已经迁入的目标不再是空壳，不能继续按孤儿删除。**

本轮运行真实route、套餐服务、provision/upgrade和movePersonalAssetsToEnterprise，仅替换数据库/外部IO，在赠送迁移边界注入失败：

- 返回HTTP500。
- 原个人空间仍存在且未归档。
- 实际资产updateMany已经将workspaceId改到新企业空间。
- catch继续删除新空间及成员。
- 最终内存资产仍引用新空间ID，但该空间已不存在；原先写的0元SUCCESS记录仍在。

证据见verification.json的`delete_gift_IO_fails_after_asset_move_cleanup_deletes_destination`。

边界：这是故障注入的隔离逻辑验证，不是线上事故证明。当前Prisma的asset、document模型只有workspaceId索引，没有对应workspace关系；未查询部署库是否另有外键。因此可确认代码在资产迁移提交后仍尝试删除目标；真实库若允许删除会造成不可达引用，若额外外键阻止删除则补偿失败，均不是可靠恢复。不能直接声称物理文件已删除或线上已丢数据。

修复建议：本批优先在任何下单/写入前明确阻断自助delete迁移方式，三个页面诚实显示暂不可用；保留原地升级和并行保留。不要为本次补修仓促跨资产/额度重建事务。后续恢复该能力前，必须单独验证迁移、赠送、归档与恢复；不能只取消删除却把半完成迁移伪装成功。

## D2 / P2：快照固定了写入内容，但没有执行已指定的“配置变化拒绝”规则

位置：`src/lib/workspace-upgrade-service.ts:97`、`src/app/api/workspace/upgrade/route.ts:207–215`。

当前输入增加verifiedPlanConfig，存在时跳过再次读取。**这是本次有效的改进**，可防止收费价格、新增资源被下一次读取覆盖进免费开通；并非此前P1反例依旧。

但R0-A3指令同时要求配置变化、停用等在写前拒绝重新确认。IDE自行选择不再核对，并将其描述为“消除时序窗口”。两者不同：固定快照避免内容漂移，但不会知道管理员已经停用该套餐。

独立验证在实际命名IO边界、业务写入之前修改内存中的当前配置为停用/收费/更高配额。实际仅查询套餐1次，仍HTTP200/free:true，按旧额度开通，账单为0。**没有以新收费价写SUCCESS，也没有免费获得新配额**；本项是未履行既定确认规则，不应再次夸大成当前可任意领取收费PRO。

修复：保留同一服务端快照贯穿写入；在本次写决策之前核验当前记录与已确认关键事实一致，发生变化就返回明确可重试确认错误，不能重新取新配置覆盖。若日后选择“请求内旧报价承诺有效”的政策，应作为显式业务决策，而不能在报告里悄悄改验收规则。本轮不新增报价有效期/优惠规则/数据库版本列。

## D3 / P2：验收测试没有覆盖其声称的场景，独立页仍缺业务成功判断

位置：`src/app/api/__tests__/r0a3-combo-regression.test.ts:6–9,88–92,178–205`；`src/app/workspace/upgrade/page.tsx:173–209`。

新增测试的两条“快照/变化”用例实际都使用不变的FREE_ROW，没有在执行过程中变价/停用；标题写maxMembers，但只断言plan/type；workspacequota写操作仍返回固定对象，未保存最终配额；文件没有导入或执行任一页面处理函数，却声称覆盖三页面状态契约。报告中用客户端伪造配置的后端测试作为页面状态证据，也不成立。

本轮额外执行实际三个handler、替换fetch/浏览器接口，共24种情况，确认：

- 正常payUrl待支付，三个入口均不写已开通标记或调用完成回调。
- 原先两个弹窗“success且缺payUrl/free”的误报已消除。
- **独立升级页只检查HTTP状态，不检查result.success。** `{success:false,free:true,workspaceId:"ws1"}`仍显示成功、写personalWorkspaceUpgraded=true并跳转。
- 三入口收到`{success:true,free:true}`但缺workspaceId仍按已开通处理，没有完整验证完成响应。

后两项是异常/不一致响应下的防御问题；没有证据说现有后端正常路径会返回这些形态，更不等于后端已错误授予权益。修复应按明确协议判断成功，失败保留选择；正式新增三个实际handler/组件的行为回归，不能以源码注释或历史JSON代替。

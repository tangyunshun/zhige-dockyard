## 3. 审计事实要求

采用既有operationlog表，不新增表/迁移/服务/审计框架。复用既有操作者、action及createdAt，补齐：

- 目标：具体配置键或计划/公告ID，创建记录必须记录实际生成的ID；同一次计划同步维护开关时要能看到两个实际目标。
- before/after：仅相关配置或字段的必要旧值/新值，来自本次事务真实读取/写入结果，不能把客户端声称的旧值或变更前根客户端缓存读数冒充实际数据库旧值。
- 开关：实际维护状态前后，以及本次确实写入的说明/预计时长；计划同步改模式也要记录模式及实际写入说明。
- 公告/计划：创建记录新ID与必要创建事实，修改记录确实变更的必要字段，删除记录原目标必要事实及删除后的事实；公示切换要有实际前后公示状态。
- 更新设置/版本：只记录实际涉及的设置或版本变化，未传systemVersion不能导致其他变更无详情；无变化可明确记录before=after或changed=false，不虚构修改。

不要求保存整张表或整个systemconfig；不记录token、会话、密钥、用户原始材料，不引入全站日志展示改造。公共GET不能因审计补修产生审计写。

在同一现有事务内取得必要旧事实、完成相关配置写、形成真实新事实并写审计；根据现有实现选择让writes返回审计事实或等价最小方案。所有持久化使用tx，禁止根客户端逃逸。审计失败必须回滚配置/会话；缓存仅在事务提交成功后更新或失效，不能提前发布。

如果为取得真实旧事实需把相关读/计算移入现有事务，只在当前动作做最小调整；不借此重做全局并发、锁、缓存架构。读取失败不能编造空旧值并标为可靠审计；必要时该写请求诚实失败并零提交。不要为了新增审计而清洗/删除无关历史记录。

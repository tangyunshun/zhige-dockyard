## 一、用户流程、可见交付和范围

目标流程：已授权用户上传/选择文件 → 在有界资源内提取或预览 → 正常小文件得到原有结果；超时、取消、过大或繁忙时得到真实原因；解析停止并回收资源后才放回容量。解析失败不能继续当作有效材料调用模型/扣费；资料上传如已落盘预留，要继续走F13既有失败清理协议。

实际范围：

- `src/lib/text-extract.ts` 及完成隔离执行、预算、共享准入必需的最小模块/worker入口；
- `src/app/api/studio/extract-text/route.ts`；
- `src/app/api/studio/handler.ts`中现有解析调用、必要的异常接线（文件材料、已存资料读取、upload_doc）；
- `src/app/api/workspace/assets/[assetId]/preview/route.ts`中的XLSX、mammoth及文本兜底重解析；
- 必要的解析专用共享准入模型、离线迁移、测试及部署/回滚说明。

不改F13文件键、存储计量、清理认领、私密授权或共享引用规则；不顺手重构大handler。预览返回已鉴权图片/PDF文件URL的非重解析分支保持，不新增扫描PDF转换、视觉模型或新格式支持，不做预览页面重设计。

## 二、K01：真正停止非合作解析，不能只停止等待

已知问题：独立extract-text仍用Promise.race返回空串；WithTimeout对OfficeParser只发送AbortSignal却不能结束工作。OCR已有terminate能力，保留并补测，不推倒这部分重做。

要求：

1. 给Office/OOXML/表格/压缩包/旧Office等重解析建立可终止的执行边界。采用当前Node部署可支持的最小隔离任务方案；不新增外部解析服务、付费API或通用队列平台。
2. 硬deadline、请求取消、worker崩溃和初始化失败，都应停止当前解析及其嵌套工作，回收worker/子任务/临时资源。超时以后到达的文本不能再成功返回或创建成功结果。
3. 不能只Promise.race、置一个aborted布尔值或把响应改504。要证明解析执行本身已停止；同步CPU重活不能靠同一事件循环的计时器假装可中断。
4. 现有OCR的terminate、初始化尚未完成时取消、重复取消等保护保持；上层执行边界还要覆盖非OCR路径。失败/取消不重启另一条无预算降级链路。
5. 计时器、取消监听、worker通信和输出都有明确收口。隔离任务实际结束确认前不能给新请求腾出名额；结束确认失败须保守保留/隔离占用并可诊断，不能让未知后台工作叠加。
6. worker入口的运行时、路径/产物与当前Next.js部署兼容。不能只在tsx里能跑，构建后的入口找不到。提交隔离环境下的worker产物定位与启动/终止证据；构建被环境阻断就明确记录发布门，不虚称生产通过。

验收必须把预检中的两条变成正确结果：Office超过期限后任务确实终止、迟到文本不被接收；3个超时解析不能在后台仍活着时释放名额并启动第4个。另测主动取消、初始化晚到、执行异常、正常完成与重复清理。

## 三、K02：全请求与嵌套解析共享有限资源预算

现有20MB是独立提取接口的大小限制，任务file模式另有100MB绝对上限/合同约束；不要误写为全系统同一既有上限。现有压缩包深度及每层20条限制有价值，但不是全任务资源预算。

要求：

1. 在大buffer分配和重解析前尽早核验输入大小；实际读取字节仍需核验，不能只信客户端Content-Length或扩展名。保留各入口既有更严格限制，不静默放宽。
2. 多文件请求及嵌套压缩包共用同一根预算：总输入/实际解压字节、条目数、层数、累计输出、总deadline及工作量上限，不能每递归一次或换一个文件就重新获得完整额度。
3. OOXML/ODF本身也是压缩容器，手工XML降级和OfficeParser不能绕过解压预算。解压前预检和实际展开都受限制，不能只相信压缩包声明大小，也不能getData全部分配后才统计。
4. PDF页数/文本规模、图片尺寸/像素、表格工作表/单元格、输出文本/预览数据等设置有限服务端技术上限；时间/CPU/内存边界与隔离执行配套。内存控制说明覆盖范围，不能把仅限制字符串长度等同于限制解析内存；无法安全支持的输入应明确拒绝。
5. 预算超限是明确失败/限制，不静默截断后声称整份材料已完整解析。已支持格式的正常小文件和中文编码保留；纯图无文字、空文本沿用诚实反馈，不把二进制乱码当正文。
6. 真实0字节存储上传按F13仍可保存元数据/对象；不能因本批把它一律当非法存储。模型任务原有无有效文本拒绝、不调用模型/不扣点的规则保持。
7. 原有3个并发/20次每分钟/60秒作为已知基线，新增平台资源及格式预算集中在最小服务端策略处，写清数值、单位、依据、适用入口和测试覆盖。它们是技术资源阈值，不是收费规则，不允许浏览器覆盖，不建设新管理页面；无法证明的生产容量按部署前置条件报告，不编造压测/盈利结论。

验证用受控小夹具与小预算制造超限，不用真实大文件、压缩炸弹或高内存试压。必须覆盖嵌套预算不能重置、伪装扩展名不能绕过、达到限制后降级链路不继续跑、合法小文件输出保持。

## 四、K03：跨实例共享原子准入与资源回收

当前Map只能限制单实例，且Studio任务、上传和预览未共享其名额。不能用多份Map或单进程队列声称已经解决跨实例预算。

要求：

1. 所有重解析入口使用同一最小共享准入：服务端用户身份、用户并发/频次、平台总并发/工作预算有有限边界，检查与认领原子完成。两个独立实例不能各自获得整份额度而超额。
2. 结合现有MySQL/Prisma实现必要的解析专用认领/租约。可参考现有claimToken模式，不得挪用退款、计费或模型注册表锁的数据；不得把registrylock或任何数据库事务持有整个慢解析期间。没有已部署Redis的证据，不新增Redis外部依赖来交差。
3. 认领有唯一身份/所有者令牌，释放和续约按持有者校验，不能重复归还或让旧执行者释放新租约。内层递归使用根预算，不重复认领成新的免费额度。
4. 成功/失败/取消/超时后，只在工作确认结束时释放执行容量。租约过期不等于物理工作已停止；期限、硬deadline、实例退出与任务终止策略要一致，防止过期回收时旧worker仍跑。
5. 进程崩溃、重启、租约中断和释放提交失败有有限恢复办法，不能永久卡槽，也不能盲目腾槽。相关状态记录有界，不能靠永久累积解析记录制造新的无上限成本。
6. 共享存储缺delegate/缺表/列或不可用时，返回稳定未就绪503，在任何重解析前拒绝；不能静默回退为本机Map无限放行。业务请求中禁止建表/迁移。纯文本已有content可直接使用而未启动重解析的路径，不必额外制造worker。
7. 发布/迁移/回滚说明清楚：新模型只服务本批解析资源准入，离线迁移可审阅；真实apply未授权，不修改既有存储或账务表。

验收：两个独立服务实例共享同一有条件求值的隔离后端；同用户与不同用户均无法突破平台/用户边界；拒绝发生在worker启动前；重复释放、迟到释放、崩溃/租约到期和后端失败均保守且能恢复。不以模拟结果声称真实MySQL并发验收。

## 五、K04：实际入口接线与错误结果

错误至少可区分超时、取消、资源超限、繁忙/限流、共享准入未就绪、无文字和真实解析异常，给稳定code与人能理解的信息。不要统一吞成空字符串、普通无文本或成功；也不要泄露原文、密钥或内部堆栈。已有前端能显示后端错误即可，不重做页面。

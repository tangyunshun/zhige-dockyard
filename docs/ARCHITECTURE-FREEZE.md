## 2. 系统定位冻结

知阁舟坊定位为**面向个人和企业的 AI 工作组件平台**。它既不是一个单纯展示/购买插件的“组件市场”，也不是一个普通的“文档/知识库协作工具”，而是将软件研发生命周期（从 RFP 解析、系统设计、PRD 生成到项目验收）的各个节点，通过 AI 效能组件、多租户工作空间和知识流沉淀有机整合起来的效能中枢系统。

系统核心实体模型关系与依赖冻结如下：
*   **用户**：拥有全局唯一的身份标识、角色属性和会员套餐限制。
*   **空间**：是用户开展工作的物理与数据安全屏障。用户进入系统后必须先选择工作空间（未选择时系统会自动兜底或引导切换）。**工作空间是工作执行的上下文载体。**
*   **组件**：是平台提供的原子能力单元（如标书解析、原型设计等）。组件必须且仅能在特定的空间上下文被使用。
*   **任务**：组件的单次运行实例。**每次用户点击或使用组件时，后端都必须生成一条任务记录**，不能仅仅在页面上临时计算并渲染。
*   **资料**：用户上传到当前空间下的原始输入材料，为组件运行提供语境基础。
*   **结果**：组件执行任务后产生的输出资产，属于临时的、多版本的快照数据。
*   **知识库**：空间或全站可复用的规范、术语和案例资产。**结果决不能自动进入知识库**，必须经过用户的二次确认或管理员审核才能发布沉淀。
*   **会员与企业**：限制使用配额的大纲。企业工作空间需要具备配套的成员管理、岗位权限分配、资源统计分析和操作审计日志等高级能力。

## 3. 当前真实路由盘点

本章基于当前 `src/app` 下的路由目录结构进行真实盘点，对已有路由的职责与权限红线进行强制性封存。

### 3.1 公开页面 (免登录态)

*   **官网首页**
    *   **当前路由**：`/` (对应 `src/app/page.tsx`)
    *   **当前职责**：产品功能展示、效能提效宣传及客户 Demo 申请。
    *   **用户能做什么**：浏览公开的营销文案、提交申请 Demo 预约表单。
    *   **用户不能做什么**：访问任何工作空间、查看组件大厅中的收藏、执行任何 AI 组件。
*   **价格方案页**
    *   **当前路由**：`/pricing`
    *   **当前职责**：展示免费版、黄金版、白金版的套餐额度及价格信息。
    *   **用户能做什么**：查看套餐明细，点击“购买/升级”（未登录时触发重定向至登录页）。
*   **公开组件大厅**
    *   **当前路由**：`/studio` (由 `/market` 与 `/capabilities` 重定向合并)
    *   **当前职责**：展示平台已发布的组件功能与优秀的结果快照。
    *   **用户能做什么**：搜索组件、浏览组件的分类与说明、查阅公开的组件评测结果。
    *   **用户不能做什么**：一键安装组件到空间、装配运行参数、点击 simulate 模拟执行。
*   **开发者文档与中心**
    *   **当前路由**：`/docs` 与 `/developers`
    *   **当前职责**：展示平台使用指南与 API 开发者集成手册。
    *   **当前重复/残缺**：`/docs` 与 `/developers` 呈现的内容及结构几乎完全一致，属于极高重复且残缺的体验，后续需合并为一个统一的开发者指南页面。
*   **辅助公开页**
    *   **当前路由**：`/solutions` (解决方案) | `/security` (私有化与安全) | `/privacy-policy` (隐私政策) | `/terms-of-service` (服务条款)
    *   **当前职责**：提供静态营销和法律合规展示。

### 3.2 认证页面

*   **登录页 / 注册页 / 忘记密码页**
    *   **当前路由**：`/auth/login` | `/auth/register` | `/auth/forgot-password`
    *   **当前职责**：用户身份通行证。
    *   **重定向规则**：如果用户已处于登录态，再次访问这些页面时，系统必须自动重定向。
    *   **登录成功兜底入口**：**用户成功登录后，系统重定向默认入口必须强行为 `/workspace-hub`**，严禁直接跳转至组件大厅或特定个人空间。
*   **注销撤销页**
    *   **当前路由**：`/auth/cancel-deletion`
    *   **当前职责**：在 7 天冷静期内，为已申请注销的用户提供撤销清退、恢复 active 状态的通道。

### 3.3 用户中心页面

*   **当前路由族**：`/user/dashboard` | `/user/profile` | `/user/settings` | `/user/security` | `/user/membership` | `/user/activities` | `/user/components`
*   **职责定位**：**属于个人账号的辅助配置与流水管理，绝非具体工作执行的主场景。**
*   *注：个人中心页面应避免承担复杂的组件配置和协作逻辑，仅作为用户个人属性（头像、密码、偏好、账单）的更改场所。*

### 3.4 空间中枢

*   **当前路由**：`/workspace-hub` (对应 `src/app/workspace-hub/page.tsx`)
*   **职责定位**：**登录成功后的唯一默认入口。**
*   **冻结规则**：
    *   它不是具体个人的独立工作空间。
    *   它不是组件大厅。
    *   它不是具体工作执行及 PRD 设计页面。
*   **核心职责**：
    1.  查看当前用户加入和拥有的所有空间列表。
    2.  提供快捷入口，引导创建默认的个人空间。
    3.  向导式创建新的企业协作空间。
    4.  输入 6 位邀请码，加入他人的企业空间。
    5.  点击切换当前的活跃工作空间（将空间 ID 绑定至 Session/User.lastWorkspaceId）。
    6.  点击空间卡片，正式进驻具体的工作操作台。
*   *遗留重复项：当前项目中并存的 `/user/workspace-hub` 是极高重复的旧版中枢，后续必须废弃，但在本次重构前禁止直接删除。*

### 3.5 空间操作台

*   **当前路由族**：`/workspace/[id]` (首页重定向) | `/workspace/[id]/studio` (组件工坊) | `/workspace/[id]/members` (空间成员) | `/workspace/[id]/settings` (空间设置) | `/workspace/[id]/stats` (统计分析) | `/workspace/[id]/components` (空间组件管理)
*   **职责定位**：特定空间内部的具体工作与设计执行场所。
*   **界面布局冻结**：**空间操作台严禁做成长滚动的“大杂烩”页面**。必须使用分层 Tab 切换或左侧局部二级导航结构进行异步渲染。

#### 基础 Tab (对空间内全员可见)

1.  **总览 (Overview)**
    *   **职责**：展示空间基本情况、Token 算力警告及最近运行的动态。
    *   **用户第一步**：预览是否有需要审批的加入申请。
    *   **操作限制**：普通成员无权修改空间基本属性。
2.  **快速任务 (Quick Run)**
    *   **职责**：展示高频组件的快捷配置表单，实现秒级运行。
    *   **用户第一步**：选择合适的模板并快速发起 AI 模拟执行。
3.  **组件管理 (Components)**
    *   **职责**：绑定、配置及管理本空间可使用的组件库。
    *   **能操作什么**：添加绑定大厅里的公开组件，管理组件的空间专属入参配置。
    *   **操作权限**：仅 `COMPONENT_MANAGER`、`ADMIN`、`OWNER` 可以执行组件绑定及配置修改。
4.  **组件工坊执行台 (Studio)**
    *   **职责**：装配参数并在线 simulate 执行组件。
    *   **能操作什么**：输入文本参数、引用资料中心文件、发起 simulate 并查阅运行日志与进度。
    *   **操作权限**：普通成员只能执行被岗位白名单允许的组件。
5.  **资料中心 (Materials)**
    *   **职责**：管理空间专属的原始输入资料（PDF, Docx 文件）。
    *   **能操作什么**：上传素材文件、分类标签设置。
6.  **结果中心 (Results)**
    *   **职责**：管理本空间下的任务执行产出成果（PRD, 架构设计图等）。
    *   **能操作什么**：查阅、下载、发起“沉淀至知识库”。
7.  **空间知识库 (Knowledge)**
    *   **职责**：查看本空间沉淀的最佳实践。
    *   **能操作什么**：查阅知识条目、作为大模型组件运行的 RAG 上下文。
8.  **设置 (Settings)**
    *   **职责**：修改空间基本信息（名称、Logo、简介）。
    *   **操作权限**：仅管理员以上可见并修改。

#### 企业管理员额外 Tab (Owner/Admin 可见)

1.  **成员管理 (Members)**：生成 6 位协作邀请码、移除成员、分配物理角色。
2.  **权限与岗位 (Permissions)**：配置“岗位”并关联成员，设置岗位对组件的 execution 读写控制。
3.  **使用统计 (Stats)**：分析 Token 与存储的消耗折线图。
4.  **日志审计 (Audit Logs)**：查看高危操作审计。

### 3.6 管理后台

*   **当前路由族**：`/admin` | `/admin/users` | `/admin/workspaces` | `/admin/components` | `/admin/membership` | `/admin/orders` | `/admin/operation-logs` | `/admin/settings` | `/admin/administrators` | `/admin/permissions` | `/admin/maintenance`
*   **职责定位**：平台级系统运维与安全总控。
*   **冻结规约**：
    *   **禁止将平台管理后台塞入普通前台的主导航栏**。
    *   **后台唯一入口必须是右上角头像下拉菜单中的“管理中心/平台后台”**，且仅对被分配了后台管理员身份的用户进行渲染。
*   *遗留死路由：`/platform-admin` 重定向路由属于无用路由，后续重构时应清理。*

## 4. 导航结构冻结

### 4.1 未登录用户主导航
*   **菜单结构**：组件大厅 (`/studio`) | 解决方案 (`/solutions`) | 私有化与安全 (`/security`) | 价格方案 (`/pricing`) | 文档中心 (`/docs`)
*   **动作限制**：未登录用户仅能查阅公开营销内容，**绝对禁止**执行任何组件、上传任何文件、访问具体空间、查看非公开任务结果、或进入管理后台。

### 4.2 已登录用户主导航
*   **菜单结构**：空间中枢 (`/workspace-hub`) | 组件大厅 (`/studio`) | 任务中心 (`/tasks`) | 知识库 (`/knowledge`) | 文档中心 (`/docs`)
*   **强制流转死线**：用户登录成功后，**首屏渲染路由必须是 `/workspace-hub`（空间中枢）**。禁止默认引流至组件大厅、特定工作空间或管理后台。

### 4.3 空间内二级导航 (左侧边栏 / 顶部 Tab)
*   **物理卡关硬约束**：
    *   **基础成员（MEMBER/VIEWER）仅可见**：总览 | 快速任务 | 组件 | 任务 | 资料 | 结果 | 知识库 | 设置（只读）
    *   **企业管理员（OWNER/ADMIN）额外可见**：成员 | 权限 | 统计 | 日志
    *   **前后端协同防御**：前端应根据用户的岗位角色自动隐藏无权访问的 Tab 入口，**后端 API 必须配合进行垂直越权拦截**，不能只依赖前端隐藏作为安全防护。

### 4.4 头像下拉菜单

头像下拉菜单必须严格遵守细粒度的角色控制，禁止越权暴露入口：

```
+-----------------------------------+
| 登录用户头像下拉菜单              |
+-----------------------------------+
  ├── 个人中心 (/user/profile)       ---> 所有人可见
  ├── 账号安全 (/user/security)      ---> 所有人可见
  ├── 会员与额度 (/user/membership)  ---> 所有人可见
  ├── 开发者设置 (/user/api-keys)    ---> 所有人可见
  ├── 帮助与反馈 (/docs)             ---> 所有人可见
  ├── 退出登录                       ---> 所有人可见
  |
  +-- [动态角色隔离控制]
  ├── 企业管理                       ---> 仅企业空间管理员 (OWNER/ADMIN) 可见
  ├── 组件管理                       ---> 仅组件管理员岗位可见
  ├── 知识库管理                     ---> 仅知识库管理员岗位可见
  ├── 平台后台                       ---> 仅平台管理员 (PLATFORM_ADMIN) 可见
  └── 管理中心                       ---> 仅超级管理员 (SUPER_ADMIN) 可见
```

## 5. 角色与权限体系冻结

### 5.1 平台级角色 (全站范围)
1.  **`SUPER_ADMIN`**：系统最高特权人，拥有对后台所有功能及系统配置的完全读写权，后台菜单默认完全放行。
2.  **`PLATFORM_ADMIN`**：平台普通管理员（运营、财务、客服人员）。不具备全量后台权限，菜单及 API 可访问性必须严格依赖 `src/lib/admin-permissions.json` 中被分配的权限包进行细粒度控制。
3.  **`USER`**：普通注册用户，无权访问平台级后台资源。

### 5.2 空间级角色 (目标架构，后续扩展)
在工作空间协作范围内，平台冻结如下三级物理角色及逻辑岗位角色体系（目前代码仅支持 OWNER/ADMIN/MEMBER 物理角色，其余岗位级角色标记为后续扩展，本次不修改数据库）：
1.  **`OWNER` (空间所有者)**：空间的创建者，拥有空间内全部管理权与最高支配权。
2.  **`ADMIN` (空间管理员)**：辅助 Owner 进行空间维护，可邀请/踢出成员、分配岗位，但无权删除工作空间。
3.  **`COMPONENT_MANAGER` (组件管理员，后续扩展逻辑角色)**：岗位含有组件管理员标识的成员，专职负责空间内组件的安装、绑定及参数默认值配置。
4.  **`KNOWLEDGE_MANAGER` (知识库管理员，后续扩展逻辑角色)**：岗位含有知识库管理员标识的成员，负责原始资料的录入及组件结果沉淀为知识库的审核流程。
5.  **`MEMBER` (空间常规成员)**：可以在被岗位授权的组件名单范围内进行装配与模拟执行。
6.  **`VIEWER` (只读访客，后续扩展逻辑角色)**：只能查看空间内数据，禁止执行任何组件、修改设置或上传文件。

### 5.3 超级管理员后台菜单
`SUPER_ADMIN` 登录后，后台左侧菜单默认呈现全量菜单：
`后台总览` | `用户管理` | `企业空间管理` | `组件管理` | `会员套餐管理` | `订单管理` | `内容管理` | `文档管理` | `通知公告` | `审计日志` | `系统设置` | `管理员管理` | `权限配置` | `维护模式`

### 5.4 平台管理员后台菜单 (PLATFORM_ADMIN)
平台管理员登录后，后台左侧菜单必须根据其权限列表进行动态匹配显示，无权访问的菜单直接进行物理隐藏：
*   **用户管理**：要求拥有 `user:read` 权限包
*   **企业空间管理**：要求拥有 `workspace:read` 权限包
*   **组件管理**：要求拥有 `component:read` 权限包
*   **订单管理**：要求拥有 `order:read` 权限包
*   **内容管理**：要求拥有 `content:read` 权限包
*   **文档管理**：要求拥有 `document:read` 权限包
*   **通知公告**：要求拥有 `announcement:read` 权限包
*   **审计日志**：要求拥有 `audit:read` 权限包
*   **系统状态**：要求拥有 `system:health_read` 权限包
*   **默认绝对不显示**：`系统设置`、`管理员管理`、`权限配置`、`维护模式`、`会员套餐管理`（除非超级管理员单独授权）。

### 5.5 后端校验金科玉律
*   **双重卡关原则**：前端控制侧边栏隐藏仅作为改善用户体验的交互设计，**后端 API 必须进行绝对的权限校验**，杜绝通过直接拼接 URL 绕过权限检查。
*   **角色隔离红线**：超级管理员拥有全部平台和空间权限；平台管理员只拥有被赋予的权限；**企业管理员只能进入企业空间管理，绝对禁止访问任何平台级的后台管理端。**

## 6. 任务执行模型冻结

任务是组件模拟运行的实体审计追踪。**每次用户在空间内或者组件大厅触发模拟运行 (Simulate) 时，必须且只能在数据库中持久化实例化为一条任务记录**。禁止出现仅在前端页面上进行“即时大模型计算”而无任务日志的情况。

### 6.1 任务生命周期模型 (目标状态机)
```
[DRAFT] ─(提交)─> [READY] ─(执行)─> [RUNNING] ─┬─> [COMPLETED]
                                              ├─> [NEEDS_REVIEW] ─(通过)─> [COMPLETED]
                                              ├─> [FAILED]
                                              └─> [CANCELED]
```
*   `DRAFT`（草稿）：已填写参数，尚未点击运行。
*   `READY`（就绪）：已点击运行，任务分配并排队。
*   `RUNNING`（执行中）：后台核心或 AI 大模型正在计算并输出中间结果。
*   `NEEDS_REVIEW`（待审核）：由于部分高价值组件容易产生格式偏差，模型输出初步结果后会进入待审核状态，必须由项目经理或系统分析师进行人工确认或微调。
*   `COMPLETED`（已完成）：计算成功，结果快照已保存，Token 算力已正确扣减。
*   `FAILED`（已失败）：运行异常，记录了具体的报错原因。
*   `CANCELED`（已取消）：任务在就绪或运行时被用户中止。
*   `ARCHIVED`（已归档）：历史任务进行分区封存。
*   *注：当前代码尚未完整实现 NEEDS_REVIEW、ARCHIVED 状态，此项作为后续迭代的“目标模型”，本次不改动数据库表结构。*

### 6.2 任务强关联实体约束
任务 (`componenttask` 表) 必须在底层强关联以下字段，严禁使用弱类型或脱离关联的散装结构：
*   **所属用户 (`userId`)**、**所属工作空间 (`tenantId`/`workspaceId`)**、**执行组件 (`componentId`)**
*   **输入资料**：记录关联读取了资料中心的哪个文件。
*   **执行参数**：以 JSON 格式固化单次运行的输入参数和配置。
*   **结果与状态**：保存输出物快照、当前状态标识。
*   **耗用额度与审计日志**：扣减的 Token 算力数量、任务操作审计事件。

### 6.3 派发与执行规则
*   **大厅触发**：从公开组件大厅发起试用时，必须弹出提示框**强制让用户选择或确认归属的工作空间**，并在该空间的额度内执行。
*   **空间内触发**：任务直接默认归属于当前活跃空间。
*   **允许重新执行的状态**：仅限于 `FAILED`、`CANCELED` 或 `DRAFT` 状态。`COMPLETED` 状态任务属于财务/审计存根，一律禁止重新运行以防刷配额。
*   **允许导出/归档的状态**：仅限 `COMPLETED` 状态任务的结果支持导出。

## 7. 资料、结果与知识库边界冻结

为了避免工作空间内部原始文件和生成资产的无序堆积，必须严格冻结资料、结果、知识库三者的业务及逻辑边界，严防数据污染。

### 7.1 资料 (Materials)
*   **定义**：用户手动上传或从外部系统同步的**原始未加工材料**。
*   **范畴**：招标标书、系统原型图、代码源文件、运维日志记录。

### 7.2 结果 (Results)
*   **定义**：特定组件执行完成后生成的**AI 计算产出物**。
*   **范畴**：解析出来的 RFP 标书结构、大模型自动生成的 PRD 文档。
*   **冻结规则**：属于**临时或多版本快照数据**。**绝对禁止组件在完成任务时自动将结果写入知识库**。

### 7.3 知识 (Knowledge)
*   **定义**：经过开发团队或管理员人工核对、确认并具有复用价值的**模板、术语、规范、经典案例**。
*   **审核沉淀机制**：
    *   **个人知识库**：用户在个人的个人空间结果页中，点击“转为知识”，由用户自行补充索引标签并确认后固化。
    *   **企业知识库**：组件在企业空间下产生的 PRD 结果，必须由 `KNOWLEDGE_MANAGER` 或 `ADMIN` 角色的成员在结果中心进行审核、核对格式、补充标签，确认无误并点击“提交沉淀”，方能沉淀至该空间的知识库中。
    *   **公共知识库**：全站共享的公共组件模板，必须由平台管理员进行运营审核后方可发布。

## 9. 安全底线冻结

后续对项目进行任何 API 的编写、修复和安全合规化工作时，必须将其作为**红线约束**：

1.  **身份获取源强制归一**：后端接口判定当前操作人 ID 时，**禁止直接信任并读取未签名/未加密的 `userId` Cookie**。必须且只能从全局中间件验证通过后注入的 `x-user-id` 请求头中安全获取。
2.  **拒绝明文 Authorization ID**：严禁通过 replace 强行拿 Bearer 后的内容当做明文 userId 使用。在任何需要单独验证身份的子接口中，必须强制调用 JWT 签名解密并判定一致性。
3.  **斩断测试特权信道**：生产代码中严禁硬编码任何类似 `X-Test-UserId` 的隐式测试后门，本地 Mock 逻辑必须限制在本地开发环境且验证 IP。
4.  **下线零鉴权公开 API**：禁止任何含有模糊查询、泄露全网空间/用户任务结构的 debug 接口在生产路由中暴露。
5.  **空间防越权物理关卡**：**所有接收 `workspaceId` 的后端 API，必须在业务层强校验用户成员关联关系**（即查询 `workspacemember` 确认当前用户确实在该空间内），杜绝凭借空间 ID 进行水平越权。
6.  **后端校验最终防线**：前端隐藏按钮仅作为交互优化，后端在收到写入/执行等高风险操作时，必须强制进行 `requireWorkspacePermission` 岗位及角色卡关。
